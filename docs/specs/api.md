# Инженерная спецификация HTTP API

Документ описывает внутреннюю реализацию HTTP-адаптера и подготовку данных для публичного контракта. Внешние методы, объекты передачи данных (DTO), коды ответов, пользовательские ограничения и примеры являются источником правды в [`../api.md`](../api.md#общие-сведения-и-правила-контракта).

## Границы и источники сведений

HTTP-адаптер расположен в `src/http/`. Он связывает маршруты Fastify (HTTP-фреймворка) с прикладными портами, проверяет форму и синтаксис транспортных параметров, а затем переводит прикладные результаты в HTTP-ответы. Схемы маршрутов одновременно используются Fastify для проверки запросов и для построения OpenAPI.

Спецификация не дублирует пользовательские таблицы DTO, закрытые перечни значений, обязательность полей, коды состояния, значения по умолчанию и примеры JSON. Публичный контракт и наблюдаемое поведение описаны в [документе API](../api.md#общие-сведения-и-правила-контракта). Внешний Kafka REST API рассматривается только как сравнительный пример формы HTTP-интерфейса: маршруты сервиса напрямую связаны с прикладным издателем Kafka и не используют этот REST API как транспорт.

## Композиция HTTP-слоя

Файлы маршрутов находятся в каталоге [`src/http/routes/`](../../src/http/routes/), а их экспорт собран в [`src/http/routes/index.ts`](../../src/http/routes/index.ts). Каждый модуль маршрута принимает прикладные зависимости и регистрирует операцию Fastify:

- [`src/http/routes/publish.ts`](../../src/http/routes/publish.ts) обращается к сервису публикации;
- [`src/http/routes/slots-register.ts`](../../src/http/routes/slots-register.ts) — к сервису регистрации слота;
- [`src/http/routes/slots-wait.ts`](../../src/http/routes/slots-wait.ts), [`src/http/routes/slots-count.ts`](../../src/http/routes/slots-count.ts) и [`src/http/routes/slots-read.ts`](../../src/http/routes/slots-read.ts) — к запросам слотов;
- [`src/http/routes/slots-delete.ts`](../../src/http/routes/slots-delete.ts) — к сервису удаления.

[`src/http/create-app.ts`](../../src/http/create-app.ts) создаёт Fastify-приложение, отключает неявное приведение типов и удаление дополнительных свойств в AJV (валидаторе JSON Schema), регистрирует OpenAPI, затем подключает маршруты, для которых предоставлены соответствующие зависимости. Приложение само не открывает порт. Наличие зависимости для запроса слотов включает регистрацию маршрутов ожидания, подсчёта и чтения; отдельные зависимости включают публикацию, регистрацию и удаление.

Каждый маршрут задаёт метод, путь, схему, метаданные документации и обработчик. Обработчик передаёт разобранные данные прикладному сервису либо напрямую формирует ответ для результата разбора параметров.

## DTO, схемы и граница валидации

Каталог [`src/http/dto/`](../../src/http/dto/) экспортирует транспортные типы. Типы публикации и представления чтения переэкспортируются из соответствующих прикладных моделей; типы регистрации слота, проверок и ответов определены для HTTP-границы. Сводный экспорт находится в [`src/http/dto/index.ts`](../../src/http/dto/index.ts).

Каталог [`src/http/schemas/`](../../src/http/schemas/) содержит схемы JSON Schema (описания структуры данных JSON), включённые в описание маршрутов. Схемы задают допустимые типы и структуру, обязательные свойства, запрет дополнительных свойств и форму ответов. Для публикации схема допускает тип полезных данных и структуру запроса, но преобразование данных в байты выполняется прикладным кодом. Схемы параметров запроса ожидания и чтения оставляют значения строками, не преобразуют их в числа. Индекс тоже описывается строковым параметром пути.

Граница обработки проходит в следующем порядке:

1. Fastify проверяет тело, параметры пути и параметры запроса по схеме маршрута. Неявное приведение типов и удаление дополнительных свойств отключены конфигурацией приложения.
2. Маршрут строго разбирает те строковые параметры, чьи форматы и допустимые значения требуют отдельной семантики. Например, `ack` разбирается в режим подтверждения; индекс, лимит и смещение разбираются как неотрицательные безопасные целые без знака, пробелов, дробной или экспоненциальной формы.
3. Маршрут передаёт валидированные данные прикладному сервису. Семантические проверки, зависящие от состояния системы, например наличие слота и допустимость значения в заданном контексте, возвращаются как варианты прикладного результата.

Схемная ошибка Fastify переводится в `INVALID_REQUEST`. Прикладные ошибки и ошибки ручного разбора переводятся маршрутами или маппером результата. Важное исключение от общей формулировки входной ошибки: формат `index` разбирается вручную, и маршруты подсчёта/чтения отображают ошибочный результат разбора в `CHECK_NOT_FOUND`, тогда как маршрут ожидания отображает ошибку разбора индекса в `INVALID_REQUEST`. Это следует из [`src/http/routes/slots-count.ts`](../../src/http/routes/slots-count.ts), [`src/http/routes/slots-read.ts`](../../src/http/routes/slots-read.ts), [`src/http/routes/slots-wait.ts`](../../src/http/routes/slots-wait.ts) и [`src/http/parsing/query-params.ts`](../../src/http/parsing/query-params.ts); семантику такого различия для вызывающего API описывает [пользовательская документация](../api.md#проверка-индекса-по-операциям).

Подробное описание алгоритмов проверки и состояния слотов относится к инженерной архитектурной спецификации, которая создаётся в рамках согласованного плана, задачи 4. Внутренняя проверка, вычисления сроков и конфигурационные значения относятся к инженерной спецификации конфигурации, создаваемой в рамках согласованного плана, задачи 5.

## Разбор параметров

Реализации разбора экспортируются через [`src/http/parsing/`](../../src/http/parsing/). `parseStrictInteger` принимает только десятичную запись неотрицательного безопасного целого; отсутствие значения представляется отдельно от ошибочного значения. `parseAckMode` различает разрешённые текстовые варианты режима подтверждения и возвращает внутренний режим.

`parseWaitParams` сначала разбирает индекс, затем параметры количества и тайм-аута, после чего возвращает либо готовую структуру, либо отдельный результат ошибки индекса/параметров. Значение тайм-аута по умолчанию передаётся в парсер зависимостью маршрута уже в миллисекундах. `parseReadParams` сначала разбирает индекс, затем смещение и лимит выборки; результат разделяет ошибку индекса и ошибку пагинации. Границы и значения по умолчанию пользовательских параметров приведены в [описании методов API](../api.md#асинхронное-ожидание-записей) и [чтении записей](../api.md#чтение-записей-проверки).

## Преобразование результатов и ошибок

[`src/http/responses/result-mapper.ts`](../../src/http/responses/result-mapper.ts) сопоставляет варианты прикладных результатов с HTTP-ответом. Маршруты вызывают соответствующий маппер, устанавливают код состояния и отправляют его тело. Для чтения маршрут сначала представляет записи; маппер чтения получает только уже подготовленные DTO либо неуспешный прикладной результат.

[`src/http/responses/error-mapper.ts`](../../src/http/responses/error-mapper.ts) централизует сопоставление машинных кодов с HTTP-кодом и безопасным русскоязычным сообщением. Здесь формируются общие ошибки `400`, `404`, `409`, `500` и `503`; код `504` при тайм-ауте формируется маппером результата ожидания вместе с пустым объектом. Ошибки валидации Fastify классифицируются в этом модуле как `INVALID_REQUEST`. Неожиданная ошибка логируется без передачи внутренней причины клиенту и отображается как `INTERNAL_ERROR`/`500`.

[`src/http/routes/error-handler.ts`](../../src/http/routes/error-handler.ts) устанавливает обработчик Fastify на маршруте. Он применяет маппер валидации, а остальные неожиданные исключения передаёт в маппер внутренней ошибки и отправляет подготовленный ответ. Прикладные результаты `404`, `409` и `503` возникают в прикладных сервисах и превращаются в HTTP-представление маппером результата; `400` также может быть сформирован непосредственно маршрутом для ошибочного ручного разбора параметров.

### Точки формирования кодов и машинных причин

- `400` для ошибки схемы формируется обработчиком из [`src/http/routes/error-handler.ts`](../../src/http/routes/error-handler.ts) через `mapValidationError` и `mapErrorCode('INVALID_REQUEST')`. Такой же код формируют маршруты при ошибочном ручном разборе `ack`, параметров ожидания или пагинации. Ошибки публикации типа данных и base64, а также недопустимый топик получают `400` через `mapPublishResult`; ошибка регистрации слота получает его через `mapSlotRegistrationResult`.
- `404` для результата прикладного поиска слота или проверки формируется `mapCountResult`, `mapReadResult` или `mapWaitResult`. В маршрутах подсчёта и чтения некорректная форма `index` сразу преобразуется в `CHECK_NOT_FOUND`; для ожидания она преобразуется в `INVALID_REQUEST` до вызова запроса слота. Удаление отсутствующего слота преобразуется в `SLOT_NOT_FOUND` через `mapSlotDeletionResult`.
- `409` формируется только `mapWaitResult` для результата `slot-deleted`; `504` там же формируется для результата `timeout` и отправляется с пустым объектом, а не через тело ошибки.
- `500` для непредставимой страницы формируется в [`src/http/routes/slots-read.ts`](../../src/http/routes/slots-read.ts) при ошибке представления либо через `mapReadResult` при таком прикладном результате. Непредвиденное исключение любого маршрута проходит через `mapUnexpectedError` и получает `INTERNAL_ERROR`/`500`.
- `503` формируется `mapPublishResult` для отказа публикации, `mapSlotRegistrationResult` для отказа регистрации и `mapWaitResult` для результата штатной остановки. В этих случаях машинные причины — соответственно `KAFKA_UNAVAILABLE` или `SERVICE_STOPPING`.
- Полное соответствие машинных кодов HTTP-кодам и безопасным сообщениям централизовано в [`src/http/responses/error-mapper.ts`](../../src/http/responses/error-mapper.ts); мапперы результатов выбирают машинный код по варианту прикладного результата, а не по тексту исключения.

## Инженерные особенности операций

### Передача байтов при публикации

Маршрут публикации передаёт исходный DTO сервису публикации. Прикладная функция `encodeRecord` проверяет тело целиком, применяет типы по умолчанию и кодирует каждое значение в `Uint8Array`: текст — UTF-8, JSON — однократная сериализация с последующим UTF-8-кодированием, двоичные данные — декодирование base64. При декодировании проверяются алфавит и расположение дополнения, нулевые неиспользуемые биты, а повторное кодирование результата должно точно совпасть с исходной строкой. Ошибка любой части останавливает подготовку до вызова порта Kafka. Подробная реализация находится в [`src/application/publishing/encode-record.ts`](../../src/application/publishing/encode-record.ts).

Нативный издатель преобразует байты в `Buffer` без перекодирования и формирует сообщение для KafkaJS (клиента Kafka для Node.js). KafkaJS задаёт заголовки объектом: порядок заголовков с разными именами не сохраняется, значения повторяющихся заголовков одного имени собираются в массив и сохраняют порядок. Типовые метки относятся к HTTP-модели и не передаются Kafka. Эти детали подтверждены [`src/infrastructure/kafka/native-publisher.ts`](../../src/infrastructure/kafka/native-publisher.ts) и [`src/infrastructure/kafka/kafkajs-adapters.ts`](../../src/infrastructure/kafka/kafkajs-adapters.ts); публичные правила типов и байтов изложены в разделе [преобразования данных](../api.md#правила-преобразования-в-байты).

### Граница принятия при публикации без подтверждения

При режиме без ожидания подтверждения нативный издатель вызывает `send` с `acks: 0` и дожидается завершения соответствующего обещания. Успешное завершение до обнаруженного отказа является прикладной границей принятия и возвращается как результат `accepted-without-confirmation`. Реализация также отслеживает сигнал позднего отказа: если он приходит после принятия, он записывается в журнал, но уже сформированный HTTP-ответ не меняется; до принятия такой сигнал приводит к отказу операции. Отсутствие подтверждения брокера не означает подтверждение доставки или сохранения записи.

Эти шаги реализованы в [`src/infrastructure/kafka/native-publisher.ts`](../../src/infrastructure/kafka/native-publisher.ts); внешнее значение ответов и ограничения гарантии определены в [разделе публикации](../api.md#принятие-отправки-без-подтверждения).

### Представление страницы чтения

Маршрут чтения получает из прикладного сервиса снимок выбранной страницы. До отправки успешного ответа маршрут последовательно представляет каждую запись в DTO. При первой непредставимой записи он возвращает ошибку для всей страницы; ранее подготовленные элементы не отправляются. Лишь после успешного представления всех записей вызывается маппер успешного результата. Аналогичная предварительная проверка представимости выполняется прикладным запросом при получении снимка. Код маршрута: [`src/http/routes/slots-read.ts`](../../src/http/routes/slots-read.ts); проверка снимка: [`src/application/slots/slot-queries.ts`](../../src/application/slots/slot-queries.ts).

Преобразование одной записи, включая строгое декодирование UTF-8, разбор JSON и кодирование ключа в base64, реализовано в [`src/application/reading/represent-record.ts`](../../src/application/reading/represent-record.ts). Внешняя политика отказа всей страницы описана в [пользовательском контракте чтения](../api.md#непредставимая-запись-и-ответ-всей-страницы).

### Техническая проверка индекса

`parseStrictInteger` проверяет строковую форму и безопасный диапазон числа. Затем операции передают числовой индекс прикладным запросам, где повторно проверяется, что число является безопасным неотрицательным целым, и отдельно проверяется наличие проверки в зарегистрированном слоте. Порядок разбора параметров до обращения к слоту реализован в [`src/http/parsing/query-params.ts`](../../src/http/parsing/query-params.ts), а наличие слота и границ — в [`src/application/slots/slot-queries.ts`](../../src/application/slots/slot-queries.ts).

Фактические коды некорректной формы индекса различаются для ожидания и чтения/подсчёта, как указано выше. Пользовательский документ должен сохранять это наблюдаемое поведение согласно [сводке индекса](../api.md#проверка-индекса-по-операциям).

## Формирование OpenAPI

[`src/http/openapi/register-openapi.ts`](../../src/http/openapi/register-openapi.ts) регистрирует дополнение `@fastify/swagger` с OpenAPI 3.0.3, маршрут выдачи сгенерированного документа по `/api-docs` и дополнение `@fastify/swagger-ui`, настроенное на `/api-docs/swagger-ui`. Обработчик `/api-docs` возвращает результат `app.swagger()`, а интерфейс Swagger UI получает спецификацию по этому пути.

Схемы и метаданные операций находятся в определениях маршрутов и являются входом формирования документа: пути, методы, сводки, описания, группы, параметры, тела и схемы ответов задаются там же. Сам маршрут выдачи документа скрыт из генерируемой спецификации. Контрактная проверка [`tests/contract/openapi.test.ts`](../../tests/contract/openapi.test.ts) получает документ через HTTP и проверяет состав прикладных путей, методы, коды и схемы ответов. Это тестовая проверка контракта, а не отдельный источник описания.

Пользовательские адреса и назначение документации приведены в [разделе OpenAPI](../api.md#openapi-и-swagger-ui).

## Темы для инженерных спецификаций задач 4–5

Следующие сведения нельзя подробно раскрывать в настоящей спецификации HTTP-слоя. Они зарезервированы как задачи согласованного плана и в текущем пользовательском документе представлены только наблюдаемыми последствиями или ссылкой:

- **Задача 4, [инженерная спецификация архитектуры](architecture.md#модель-проверок-и-асинхронного-ожидания):** внутренняя модель хранения накопленных записей, порядок и конкурентный доступ к снимкам; полная семантика сопоставления проверок и повторяющихся заголовков; безопасный обход выражений языка выбора узлов JSON и защита от доступа к прототипам; жизненный цикл слота и консюмера, регистрация/откат и очистка; реестр ожиданий, гонки завершения и неблокирующая организация ожидания; единый внутренний путь удаления и освобождение ресурсов; архитектурные ограничения и решения.
- **Задача 5, [будущая `docs/specs/configuration.md`](configuration.md#проверка-конфигурации-и-вычисления-времени), создаваемая в рамках согласованного плана:** внутренний разбор и проверка конфигурации; вычисление сроков и преобразование параметров ожидания конфигурации; формирование групп консюмера; внутренние таймеры и связанные с конфигурацией значения по умолчанию.

Пользовательские архитектурные ограничения описаны в [`../architecture.md`](../architecture.md#ограничения). Пользовательские правила конфигурации остаются в [`../configuration.md`](../configuration.md#общие-правила-конфигурации). Спецификация архитектуры создана задачей 4; инженерная спецификация конфигурации создаётся в рамках согласованного плана, задачи 5, поэтому соответствующая ссылка остаётся плановой.
