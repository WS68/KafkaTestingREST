Внутреннее устройство компонентов и обработка записей описаны в [`architecture.md`](architecture.md); для параметров конфигурации выделен документ [`configuration.md`](configuration.md). Исходные требования и назначение проекта находятся в [`../readme.md`](../readme.md); правила документирования определены в [`../AGENTS.md`](../AGENTS.md).

Состав документа:

## Общие сведения и правила контракта

### Базовый путь и формат обмена

- Базовый путь всех методов — `/api/v1`. Полные пути приведены в описании каждого метода.
- Обмен выполняется в формате JSON: запросы с телом передают `Content-Type: application/json`, ответы возвращаются с JSON-телом.
- Имена полей передаются в кодовом написании и регистрозависимы: `topic`, `headers`, `name`, `type`, `data`, `value`, `key`, `checks`, `values`, `jsonPath`, `autoDeleteSeconds`, `count`, `offset`, `ack`, `id`, `n`, `timeoutMs`. Переименование полей не допускается.
- Бинарные данные на границе JSON/HTTP представляются base64-строкой. В Kafka передаются исходные байты; base64 не является форматом хранения в топике.
- Идентификатор слота — строка. Индекс проверки — целое число, отсчёт начинается с нуля и соответствует позиции элемента в массиве `checks` запроса регистрации слота.
- Успешный ответ, не возвращающий данных, содержит тело `{}`. Ответ, возвращающий данные, содержит JSON-объект или массив объектов описанной структуры.
- Тело ответа определяется описанием конкретного метода. В частности, ответ ожидания с кодом `504` содержит `{}`, а не описание ошибки. Остальные ошибочные ответы имеют единую структуру из раздела «Формат тела ошибки»; пустой JSON-объект не заменяется отсутствующим телом.

### Источники и статус уточнений

Исходный состав методов, полей и явно заданных кодов состояния сохранён при выделении API из [`../readme.md`](../readme.md). В репозитории создан только каркас: обработчики HTTP и собственная спецификация OpenAPI ещё не реализованы; проверка работающего сервиса не выполнялась. Поэтому ниже разделены утверждённые решения контракта и оставшиеся допущения; соответствие будущей реализации и собственной спецификации по `/api-docs` подлежит отдельной проверке.

В рамках задачи 04 утверждены [представление отсутствующих данных](#представление-полученной-записи), [разделение сопоставления и представления](#сохранение-сопоставление-и-представление) и [отказ всей выбранной страницы при непредставимой записи](#непредставимая-запись-и-ответ-всей-страницы). В рамках задачи 05 утверждены [ограничения условий и допустимый синтаксис JSONPath](#ограничения-условий-проверки), а точные правила совпадения и таблицы граничных случаев закреплены в [архитектуре](architecture.md#правило-совпадения). Это нормативные решения для будущих HTTP-адаптера и OpenAPI, а не допущения до появления реализации. Обоснование выбора дополнительных кодов приведено в разделе «Формат тела ошибки».

Внешний пример API Kafka REST может использоваться только для сравнения формы публичного HTTP API. Он не является зависимостью или транспортом этого сервиса: сервис всегда подключается к нативному брокеру Kafka для публикации, чтения и управления собственными группами. Внешний пример не изменяется, а требования к преобразованию типов, кодировке UTF-8, base64 и значениям по умолчанию ниже являются требованиями контракта этого сервиса.

Оставшиеся уточнения вне утверждённых решений задач 03–05 следует считать **допущениями**, а не проверенным поведением:

- необязательность `ack` и его значение по умолчанию `1`, смещение (`offset`) по умолчанию `0`, применение `defaultWaitSeconds` при отсутствии `timeoutMs` с переводом секунд в миллисекунды;
- код `201` при регистрации слота, поскольку исходные требования задают только тело её успешного ответа;
- внешние особенности, уточнённые на основе [`architecture.md`](architecture.md), включая автоматическое удаление и независимость накопления от ожиданий.

Явно заданные исходными требованиями коды и тела ответов сохраняются без изменения. Оставшиеся допущения требуют отдельного согласования. И утверждённые решения, и допущения необходимо сверить с реализацией и собственной OpenAPI-спецификацией при их появлении; этот документ не заменяет такую проверку.

### Общая структура описания методов

Каждый метод описан по единому шаблону: назначение, метод и путь, параметры пути, параметры запроса, тело запроса, тело ответа, коды состояния, особенности. Обозначения `{name}`, `{id}` и `{index}` заменяются значениями параметров пути; `0/1` означает выбор одного значения `ack`, а `NNNN`, `ms`, `N` и `M` — значения параметров запроса. Это условные обозначения, а не буквальные значения в запросе; в тела JSON-примеров они не входят.

### Сводная таблица методов

| Метод | Путь | Назначение | Успешный код |
| --- | --- | --- | --- |
| `POST` | `/api/v1/topics/{name}/records` | Публикация записи в топик через нативный клиент Kafka | `201` или `202` |
| `POST` | `/api/v1/slots` | Регистрация слота с набором проверок | `201` |
| `POST` | `/api/v1/slots/{id}/checks/{index}/wait` | Асинхронное ожидание записей под проверкой | `200` |
| `GET` | `/api/v1/slots/{id}/checks/{index}/count` | Подсчёт записей, попавших под проверку | `200` |
| `GET` | `/api/v1/slots/{id}/checks/{index}` | Чтение записей, попавших под проверку | `200` |
| `DELETE` | `/api/v1/slots/{id}` | Удаление слота до истечения `autoDeleteSeconds` | `200` |

### Рекомендуемая последовательность вызова

1. Зарегистрировать слот с проверками методом `POST /api/v1/slots` и сохранить полученный `id`.
2. Инициировать тестируемую операцию, при необходимости опубликовав запись методом `POST /api/v1/topics/{name}/records`.
3. Дождаться нужного числа записей методом `POST /api/v1/slots/{id}/checks/{index}/wait` либо проверить их количество методом `GET /api/v1/slots/{id}/checks/{index}/count`.
4. Прочитать накопленные записи методом `GET /api/v1/slots/{id}/checks/{index}`.
5. Удалить слот методом `DELETE /api/v1/slots/{id}`, если он больше не нужен.

Порядок шагов 1 и 2 важен для теста: слот наблюдает только записи, полученные после его регистрации. Консюмер начинает чтение с конца разделов топика, поэтому записи, пришедшие до открытия слота или за время, пока консюмер был закрыт, в слот не попадают. Почему это так, описано в [`architecture.md`](architecture.md).

## Формат `RecordDto`

`RecordDto` — структура записи в теле запроса публикации. Запись, полученная из Kafka, возвращается методом чтения в отдельном JSON-ограниченном представлении. Причина различия: Kafka хранит только байты и не сохраняет типовую метку из HTTP-запроса, поэтому входная типизированная модель и представление полученной записи описываются раздельно.

Исходная типовая метка при чтении не восстанавливается, поэтому представление чтения не является копией исходного запроса. При этом корректно представленный объект чтения может быть опубликован снова по правилам модели публикации: отсутствие `type` у заголовков покрывается типом по умолчанию `STRING`, а `value` с типом `JSON` допустимо для публикации. Побайтовое сохранение исходного JSON при такой повторной публикации не гарантируется, поскольку значение сериализуется заново.

### Модель публикации

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `headers` | массив объектов | Нет | Набор заголовков записи; при отсутствии запись передаётся без заголовков |
| `headers[].name` | строка | Да, если элемент задан | Имя заголовка; остаётся обычной строкой и не типизируется |
| `headers[].type` | строка, закрытый перечень `STRING`, `BINARY`, `JSON` | Нет | Тип полезных данных заголовка; при отсутствии применяется `STRING` |
| `headers[].value` | строка или JSON-данные | Да, если элемент задан | Полезные данные заголовка: строка для `STRING` и `BINARY`, JSON-данные для `JSON` |
| `key` | объект | Нет | Ключ записи; при отсутствии запись передаётся без ключа |
| `key.type` | строка, закрытый перечень `STRING`, `BINARY`, `JSON` | Нет | Тип ключа; при отсутствии применяется `STRING` |
| `key.data` | строка или JSON-данные | Да, если `key` задан | Полезные данные ключа: строка для `STRING` и `BINARY`, JSON-данные для `JSON` |
| `value` | объект | Да | Значение записи |
| `value.type` | строка, закрытый перечень `STRING`, `BINARY`, `JSON` | Нет | Тип значения; при отсутствии применяется `JSON` |
| `value.data` | строка или JSON-данные | Да | Полезные данные значения: строка для `STRING` и `BINARY`, JSON-данные для `JSON` |

### Правила преобразования в байты

- В Kafka всегда передаются исходные байты. Base64 — только представление двоичных данных на границе JSON/HTTP и не является форматом хранения в Kafka.
- `STRING`: полезные данные — текст, который кодируется в UTF-8 без добавления JSON-кавычек.
- `JSON`: полезные данные — JSON-данные, которые сериализуются в JSON ровно один раз и кодируются в UTF-8. Объект остаётся объектом и не превращается в строку с экранированным JSON. Если `data` само является JSON-строкой, кавычки и экранирование — нормальная обязательная часть её однократной сериализации, а не признак двойной сериализации; автоматический разбор текста JSON внутри строк не выполняется. Сравнение: `STRING` с `data` `foo` даёт байты `foo`, а `JSON` с `data`, равным JSON-строке `foo`, — байты JSON-текста `"foo"`, где кавычки входят в данные.
- `BINARY`: полезные данные — base64-строка, которая декодируется в исходные байты перед публикацией. Публикуются именно исходные байты, а не UTF-8-байты текста base64. Двойное кодирование запрещено: `Zm9vYmFy` превращается в байты `66 6f 6f 62 61 72` (`foobar`), а не в байты строки `Zm9vYmFy`.
- При чтении выполняется обратное преобразование согласно разделу «Представление полученной записи»: ключ представляется base64-строкой исходных байтов, заголовки — строками UTF-8, значение — разобранным JSON.
- Тип по умолчанию применяется только при отсутствии `type`: `STRING` для `key` и значений заголовков, `JSON` для `value`. Если `type` не является строкой из закрытого перечня либо форма полезных данных не соответствует типу, возвращается `400` с кодом ошибки `INVALID_RECORD_TYPE`. Некорректная base64-строка для `BINARY` даёт `400` с кодом `INVALID_BASE64`. Проверяются заголовки, ключ и значение целиком до вызова клиента Kafka; при отказе ни одна часть записи не публикуется, незаметное преобразование по умолчанию не выполняется.
- Для `BINARY` принимается стандартная каноническая base64: алфавит `A–Z`, `a–z`, `0–9`, `+`, `/`, длина кратна четырём, завершающие знаки `=` обязательны там, где требуется дополнение. Пробелы, переносы строк, URL-безопасный алфавит и ненулевые неиспользуемые биты последнего символа отклоняются; повторное кодирование декодированных байтов должно точно воспроизводить входную строку. Пустая строка допустима и представляет пустые байты. Нестроковые полезные данные для `BINARY` отклоняются как несоответствие типу `INVALID_RECORD_TYPE`.
- JSON сериализуется заново, поэтому пробелы и порядок полей исходного JSON не гарантируются. Типы `STRING` и `JSON` различаются только способом получения байтов: строка `{"foo":"bar"}` с типом `STRING` даёт UTF-8-байты этого текста, а JSON-данные `{"foo":"bar"}` с типом `JSON` дают байты сериализованного JSON. Kafka не сохраняет метку типа, поэтому при чтении исходное различие не восстанавливается.

### Форма типизированного заголовка

Для заголовка используется минимальная обратно совместимая по форме запись `{name, type, value}`:

- `name` — обычная строка, имя заголовка не типизируется;
- `type` — необязательное поле закрытого перечня `STRING`, `BINARY`, `JSON`; при отсутствии применяется `STRING`;
- `value` — полезные данные: JSON-данные для `JSON`, строка для `STRING` и `BINARY`.

Такая форма сохраняет существующее поле `headers[].value` и не вводит неоднозначное вложение `value.value`. Одновременная поддержка двух форм заголовка не предусмотрена.

### Представление полученной записи

| Поле | Тип | Назначение |
| --- | --- | --- |
| `headers` | массив объектов | Обязательное поле; при отсутствии заголовков возвращается `[]`, а не `null` и не отсутствие поля |
| `headers[].name` | строка | Имя заголовка |
| `headers[].value` | строка | Значение заголовка, полученное строгим декодированием его байтов как UTF-8; base64 не применяется |
| `key` | объект | Поле присутствует только при наличии ключа; отсутствующий ключ Kafka представлен отсутствием поля, а не `null` |
| `key.type` | строка | Всегда `BINARY`: обозначение способа представления произвольных байтов в JSON, а не исходного типа публикации |
| `key.data` | строка | Base64 исходных байтов ключа; пустые байты представлены пустой строкой и отличаются от отсутствующего ключа |
| `value` | объект | Обязательное поле успешно представленной записи; отсутствие значения Kafka не имеет успешного представления |
| `value.type` | строка | Всегда `JSON` |
| `value.data` | JSON-данные | JSON-значение любого вида, полученное разбором строго декодированных UTF-8-байтов значения, включая JSON-значение `null` |

- Произвольные байты существующего ключа представимы через base64; декодирование ключа как UTF-8 и разбор его как JSON не требуются.
- Пустые байты существующего заголовка представлены пустой строкой. Отсутствие всех заголовков отличается от существующего заголовка без значения: последнее не представимо строкой и является ошибкой представления, а не основанием удалить заголовок или заменить его значение пустой строкой.
- Отсутствующее значение Kafka, в том числе запись об удалении ключа в уплотняемом топике, не подменяется JSON-значением `null`. Байты JSON-текста `null` представимы как `value` с `type`, равным `JSON`, и `data`, равным `null`; отсутствие байтов значения — ошибка представления.
- Все значения заголовков и значение записи декодируются строго как UTF-8. Некорректные последовательности не заменяются символом замены; корректный символ U+FFFD, уже содержащийся в исходном тексте, сам по себе ошибкой не является.
- После строгого декодирования значение записи должно быть корректным JSON. Пустые байты, текст из одних пробельных символов и иной некорректный JSON являются ошибкой представления, а не пустым результатом чтения.
- Поддерживается только JSON UTF-8 для значения полученной записи; ни двоичное тело ответа, ни запасное представление значения или заголовков через base64, строку, `null` или специальный объект ошибки внутри записи не вводятся. Последствия ошибки определяет [политика всей страницы](#непредставимая-запись-и-ответ-всей-страницы).
- Исходный тип `STRING`, `BINARY` или `JSON`, указанный при публикации, в Kafka не сохраняется и при чтении не восстанавливается.

### Сохранение, сопоставление и представление

Это три разные операции, и ошибка одной не подменяет результат другой:

1. **Сохранение исходных данных.** В накопитель каждой совпавшей проверки поступает исходная запись с байтами ключа, значения и заголовков и признаками отсутствия данных, а не заранее сериализованный объект чтения. Инварианты хранения определены в [архитектуре накопителя](architecture.md#накопление-и-порядок-записей).
2. **Сопоставление условий.** Отсутствие подходящего заголовка после обработки всех одноимённых кандидатов, отсутствие значения записи, ошибка декодирования или разбора JSON при наличии условий по значению означают несовпадение соответствующих условий, а не отказ обработки Kafka. Ошибочный кандидат заголовка не отменяет совпадение другого одноимённого кандидата. Непроверяемые части записи не влияют на совпадение: запись с непредставимым значением может попасть в проверку только по заголовкам или без условий, а запись с непредставимым посторонним заголовком — в проверку по другим условиям. Точная семантика сопоставления определяется [моделью проверки](architecture.md#правило-совпадения).
3. **Представление при чтении.** Проверяется вся выбранная запись, включая заголовки, не участвовавшие в сопоставлении. Ошибка представления не удаляет и не исправляет запись, не уменьшает счётчик, не меняет порядок накопителя и не отменяет результат совпадения. Подсчёт и ожидание учитывают все накопленные записи независимо от их представимости; успешное ожидание не гарантирует успешного чтения страницы.

### Пример: публикация значения типа `JSON`

```json
{
  "headers": [
    {
      "name": "correlationId",
      "value": "corr-123"
    },
    {
      "name": "binaryTrace",
      "type": "BINARY",
      "value": "dHJhY2UtNDI="
    }
  ],
  "key": {
    "type": "STRING",
    "data": "order-42"
  },
  "value": {
    "type": "JSON",
    "data": {
      "orderId": "42",
      "status": "CREATED"
    }
  }
}
```

У заголовка `correlationId` тип не задан, поэтому применяется `STRING`. Заголовок `binaryTrace` декодируется из base64 в байты `trace-42`. Ключ передаётся как UTF-8-байты текста `order-42`, значение — как UTF-8-байты сериализованного JSON.

### Пример: публикация значения типа `BINARY`

```json
{
  "headers": [],
  "key": {
    "type": "STRING",
    "data": "order-42"
  },
  "value": {
    "type": "BINARY",
    "data": "Zm9vYmFy"
  }
}
```

Значение `Zm9vYmFy` декодируется в байты `66 6f 6f 62 61 72` (`foobar`), а не в байты текста `Zm9vYmFy`.

### Пример: представление полученной записи

```json
{
  "headers": [
    {
      "name": "correlationId",
      "value": "corr-123"
    }
  ],
  "key": {
    "type": "BINARY",
    "data": "b3JkZXItNDI="
  },
  "value": {
    "type": "JSON",
    "data": {
      "orderId": "42",
      "status": "COMPLETED"
    }
  }
}
```

Заголовок представлен UTF-8-строкой без base64 и без поля `type`; ключ — base64 исходных байтов; значение — разобранный JSON.

Пример записи без ключа и заголовков, значение которой содержит JSON-текст `null`:

```json
{
  "headers": [],
  "value": {
    "type": "JSON",
    "data": null
  }
}
```

Этот пример не обозначает отсутствующее значение Kafka: оно непредставимо по правилам выше. Выбор отсутствующего поля для ключа и пустого массива для заголовков сохраняет совместимость с формой модели публикации без добавления вариантов с `null`.

## Публикация записей в топики

### Назначение

Передача записи в топик Kafka через нативный клиент Kafka. HTTP используется только между тестом и нашим сервисом; внешний Kafka REST API не является зависимостью. Метод позволяет тесту инициировать асинхронную операцию без собственного клиента Kafka. Результат публикации не зависит от того, открыт ли слот по этому топику: попадание записи в слот проверяется только методами ожидания, подсчёта и чтения.

### Метод и путь

`POST /api/v1/topics/{name}/records?ack=0/1`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `name` | строка | Да | Имя топика, в который публикуется запись |

### Параметры запроса

| Параметр | Тип | Обязательность | Допустимые значения | Назначение |
| --- | --- | --- | --- | --- |
| `ack` | целое | Нет — допущение | `0`, `1`; значение по умолчанию `1` — допущение | Режим подтверждения отправки |

Значения `ack`:

| Значение | Смысл | Код успешного ответа |
| --- | --- | --- |
| `1` | Сервис дожидается подтверждения брокера и сообщает, что отправка подтверждена | `201` |
| `0` | Сервис не дожидается подтверждения брокера и сообщает, что сообщение принято к отправке | `202` |

### Тело запроса

Тело — объект модели публикации, описанной в разделе «Формат `RecordDto`». Обязательным является поле `value`; поля `headers` и `key` необязательны. Пример с полностью опущенными `type` показывает применение значений по умолчанию:

```json
{
  "headers": [
    {
      "name": "correlationId",
      "value": "corr-123"
    }
  ],
  "key": {
    "data": "order-42"
  },
  "value": {
    "data": {
      "orderId": "42",
      "status": "CREATED"
    }
  }
}
```

Здесь заголовок и ключ интерпретируются как `STRING`, значение — как `JSON`.

### Передача байтов нативному клиенту Kafka

- После применения значений по умолчанию сервис передаёт нативному клиенту Kafka исходные байты `key`, `value` и `headers`.
- `STRING` кодируется в UTF-8, `JSON` сериализуется ровно один раз и кодируется в UTF-8, а `BINARY` декодируется из base64 в исходные байты. В Kafka не передаётся текст base64 и не выполняется промежуточное преобразование в формат внешнего прокси.
- Массив `headers` сохраняет порядок элементов и дубликаты имён заголовков; типовая метка Kafka не передаётся, поскольку `type` относится только к границе JSON/HTTP нашего API.
- Внешний пример Kafka REST может оставаться только сравнительным описанием формы публичного HTTP API; он не является нормативным контрактом, зависимостью или транспортом реализации.

### Принятие отправки без подтверждения

При `ack=0` используется нативный режим KafkaJS без подтверждения брокера, а не подтверждаемая отправка, запущенная без обработки результата. Граница принятия определена так:

1. Сервис проверяет параметры, допустимость топика и всё тело записи, затем преобразует данные в байты. Отказ проверки возвращает `400` без вызова клиента Kafka.
2. Сервис вызывает нативную операцию отправки без подтверждения брокера и дожидается её успешного завершения на стороне клиента. Сам запуск операции, создание её асинхронного результата или помещение данных во внутренний буфер не считается принятием.
3. Успешное завершение этой операции — момент принятия: HTTP-слой фиксирует результат `202` с `{}`. Сервис не ожидает подтверждения получения или сохранения записи брокером; успешное завершение операции в этом режиме таким подтверждением не является.

Немедленный отказ клиента, ошибка подключения, получения метаданных или сетевой отправки, обнаруженная до успешного завершения нативной операции, возвращает `503` с кодом ошибки `KAFKA_UNAVAILABLE`, а не `202`. Правило действует и для асинхронного отказа операции: отказ не становится поздним только потому, что вызов уже вернул управление.

Отказ, обнаруженный после границы принятия, считается поздним: он записывается в журнал, не меняет зафиксированный `202` и не порождает второй HTTP-ответ. Если ошибка обнаружена до границы принятия, но HTTP-соединение уже разорвано, отправить ответ клиенту невозможно; это не означает успешного принятия.

`202` означает только принятие на стороне клиента Kafka. Доставка в Kafka, сохранение записи, её появление в слоте и доставка после остановки или аварии сервиса **не гарантируются**. При сетевом отказе или отсутствии подтверждения фактическая доставка может быть неизвестна; ни `503`, ни разрыв HTTP-соединения не доказывают, что запись не передана. Автоматический повтор запроса тестом может привести к дубликатам. Прикладных повторных попыток, отдельной очереди и фоновой досылки сервис не выполняет.

### Тело ответа

Тело успешного ответа (`201` или `202`) — пустой JSON-объект. Ошибки возвращаются в едином формате из раздела «Формат тела ошибки».

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `201` | Отправка подтверждена брокером; возвращается при `ack=1` | `{}` |
| `202` | Сообщение принято к отправке без ожидания подтверждения брокера; возвращается при `ack=0` | `{}` |
| `400` | Список `publisherTopics` непуст и имя топика не соответствует ни одному его регулярному выражению | Единое тело ошибки, `TOPIC_NOT_ALLOWED` |
| `400` | Неизвестный или некорректный `type`, форма полезных данных не соответствует выбранному типу | Единое тело ошибки, `INVALID_RECORD_TYPE` |
| `400` | Полезные данные `BINARY` — строка с некорректной base64 | Единое тело ошибки, `INVALID_BASE64` |
| `400` | Недопустимые параметры или структура запроса, в том числе `ack` вне `0`, `1`, отсутствующее обязательное поле или некорректный JSON | Единое тело ошибки, `INVALID_REQUEST` |
| `503` | Отказ нативного клиента Kafka или недоступность общего брокера: при `ack=1` подтверждение не получено, при `ack=0` отказ обнаружен до границы принятия | Единое тело ошибки, `KAFKA_UNAVAILABLE` |

### Особенности

- Допустимость топика определяется параметром `publisherTopics`. Правила конфигурации см. в [`configuration.md`](configuration.md). Порядок проверки до обращения к Kafka описан в [`architecture.md`](architecture.md).
- Тип задаётся закрытым перечнем `STRING`, `BINARY`, `JSON`. Значения по умолчанию применяются только при отсутствии `type`: `STRING` для `key` и значений заголовков, `JSON` для `value`. При неизвестном или некорректном `type`, несоответствии формы `data` выбранному типу или некорректной base64-строке для `BINARY` данные не публикуются и не заменяются значением по умолчанию: ошибочные данные не должны незаметно преобразовываться.
- Режим `ack` определяет, требуется ли подтверждение брокера через нативный клиент Kafka; это не подтверждение накопления записи в слоте, и публикация не изменяет состав слотов или накопление записей.
- При `ack=1` отказ нативного клиента Kafka, в том числе сетевой тайм-аут подтверждения, возвращает `503` с кодом `KAFKA_UNAVAILABLE`, а не `504` ожидания записей. Фактическая доставка может быть неизвестна. Для `ack=0` действует граница принятия, определённая выше. Внутренняя обработка отказов описана в [`architecture.md`](architecture.md).
- Метод не возвращает идентификатор слота и не содержит признака попадания записи в слот.
- Задержка между успешным ответом публикации и появлением записи в слоте определяется Kafka и сервисом не гарантируется; поэтому ожидание реализовано асинхронным с тайм-аутом.

## Регистрация слота и проверок

### Назначение

Создание слота — точки наблюдения за топиком. С момента регистрации слота начинают заполняться результаты его проверок: каждая полученная из топика запись сопоставляется с проверками слота, и подходящие записи накапливаются. Слот привязывается к одному топику и неизменяемому набору проверок; обычно слот регистрируется по идентификатору корреляции.

### Метод и путь

`POST /api/v1/slots`

### Параметры пути

Метод не имеет параметров пути.

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `topic` | строка | Да | Имя наблюдаемого топика |
| `autoDeleteSeconds` | целое, больше нуля | Нет | Срок автоматического удаления слота в секундах, отсчитываемый от момента регистрации |
| `checks` | непустой массив объектов | Да | Набор проверок слота; позиция элемента задаёт `index` в путях остальных методов |
| `checks[].headers` | массив объектов | Нет | Ожидаемые заголовки записи; пустой набор не накладывает ограничения |
| `checks[].headers[].name` | строка | Да, если элемент задан | Имя ожидаемого заголовка |
| `checks[].headers[].value` | строка | Да, если элемент задан | Ожидаемое значение заголовка — обычная UTF-8-строка, а не base64 |
| `checks[].values` | массив объектов | Нет | Ожидаемые значения, извлекаемые из значения записи по `jsonPath`; пустой набор не накладывает ограничения |
| `checks[].values[].jsonPath` | строка | Да, если элемент задан | Путь по [разрешённому синтаксису](#допустимый-синтаксис-jsonpath) внутри разобранного значения записи, а не объекта представления чтения |
| `checks[].values[].value` | строка | Да, если элемент задан | Ожидаемая строка по [правилам преобразования результата](architecture.md#преобразование-и-сопоставление-результатов-jsonpath); не произвольные JSON-данные |

### Ограничения условий проверки

Условия одной проверки соединяются логическим И. Внутри отдельного условия достаточно одного совпавшего кандидата: одноимённого заголовка либо выбранного узла JSONPath (языка выбора узлов JSON). Точная семантика имеет единый источник в архитектуре:

- [Сопоставление заголовков и повторяющихся имён](architecture.md#сопоставление-заголовков-и-повторяющихся-имён): точное сравнение имени и UTF-8-строки, независимость повторяющихся условий, отсутствие требования к количеству дубликатов и обработка ошибочных кандидатов.
- [Преобразование и сопоставление результатов JSONPath](architecture.md#преобразование-и-сопоставление-результатов-jsonpath): строки без внешних кавычек, компактная сериализация остальных JSON-значений без сортировки свойств, отсутствие результата, выбранные массивы, несколько результатов, ограничения числовой точности и таблица ожидаемых исходов.

Поля ожидаемых значений остаются строками: число, логическое значение, JSON-значение `null`, объект или массив вместо строки в `checks[].headers[].value` либо `checks[].values[].value` недопустимы; автоматическое приведение входного поля к строке не выполняется. Пустая ожидаемая строка допустима. Повторяющиеся имена заголовков и повторяющиеся пути в условиях допустимы. Поле `type` ожидаемому заголовку не задаётся; имя не типизируется, структурное сравнение заголовков не применяется.

При регистрации проверяется синтаксис всех путей; недопустимый путь или нестроковое ожидаемое значение дают `400` с кодом `INVALID_REQUEST` для всего запроса. Слот не создаётся, консюмер не создаётся и не продлевается, частичной регистрации корректных проверок нет. Отсутствие узла по корректному пути, несовместимый вид данных на промежуточном шаге, ошибка UTF-8 или разбора JSON полученной записи — несовпадение условия, а не ошибка регистрации и не новый HTTP-ответ. Отличие несовпадения от ошибки чтения определено в разделе [«Сохранение, сопоставление и представление»](#сохранение-сопоставление-и-представление).

### Допустимый синтаксис JSONPath

Поддерживается только следующий ограниченный язык, независимо от возможностей выбранной библиотеки. Путь начинается с `$`, обозначающего всё разобранное значение записи, и содержит ноль или более шагов из таблицы, соединённых без дополнительных разделителей. Пустая строка не является путём и отклоняется.

| Форма | Назначение | Пример пути |
| --- | --- | --- |
| `$` | Выбор корня; корнем может быть объект, массив или скаляр, включая `null` | `$` |
| `.имя` | Выбор собственного свойства объекта; имя начинается с латинской буквы или `_` и продолжается латинскими буквами, цифрами или `_` | `$.order.status` |
| `["имя"]` | Выбор собственного свойства объекта с произвольным именем; внутри скобок ровно одна строка в двойных кавычках по правилам JSON, включая стандартные экранирования | `$["order.id"]`, `$[""]`, `$["статус"]` |
| `[индекс]` | Выбор элемента массива; индекс — `0` либо десятичные цифры с первой цифрой `1–9`, не больше `9007199254740991` | `$.items[0].id` |
| `[*]` | Выбор всех непосредственных элементов массива или значений собственных свойств объекта | `$.items[*].id`, `$[*]` |

Пробелы вне строкового имени свойства запрещены, включая начальные и конечные; внутри такого имени пробелы являются частью имени. Индекс не содержит знака, ведущих нулей, дробной части или экспоненты. Скобочный выбор имени использует только двойные кавычки: одинарные кавычки не поддерживаются. Экранированное имя после разбора обозначает буквальное имя свойства, а не новый фрагмент пути; например, `$["a.b"]` выбирает одно свойство с точкой в имени. Выход индекса за границы массива корректен синтаксически, но не выбирает узел. Правила обхода разных видов узлов и запрета доступа к прототипам определены в [требованиях адаптера](architecture.md#безопасное-вычисление-jsonpath).

Все остальные формы запрещены, в частности рекурсивный спуск, сокращённый выбор всех свойств через точку, объединения селекторов, срезы, отрицательные индексы, фильтры, регулярные выражения, вычисляемые индексы, обращения к текущему узлу, вызовы функций, арифметические и логические выражения, расширения типов и служебные операторы библиотеки. Например, `$..id`, `$.*`, `$['id']`, `$.items[0,1]`, `$.items[0:2]`, `$.items[-1]`, `$.items[?(@.id == 1)]` и `$.items[(@.length-1)]` отклоняются с `400`, `INVALID_REQUEST`, а не принимаются как условия, которые никогда не совпадут. Пользовательские выражения никогда не выполняются как код; «песочница» не расширяет разрешённый синтаксис.

### Пример регистрации

Пример запроса:

```json
{
  "topic": "orders.results",
  "autoDeleteSeconds": 300,
  "checks": [
    {
      "headers": [
        {
          "name": "correlationId",
          "value": "corr-123"
        }
      ],
      "values": [
        {
          "jsonPath": "$.status",
          "value": "COMPLETED"
        }
      ]
    },
    {
      "values": [
        {
          "jsonPath": "$.orderId",
          "value": "42"
        }
      ]
    }
  ]
}
```

В примере слот содержит две проверки: проверка с индексом `0` требует совпадения заголовка `correlationId` со строкой `corr-123` и значения `$.status`, проверка с индексом `1` — только значения `$.orderId`.

### Тело ответа

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | строка | Идентификатор созданного слота; используется во всех последующих методах работы со слотом |

```json
{
  "id": "3f6b1a2c-9d4e-4b7a-8c1a-2e5f7a9b0c3d"
}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `201` | Слот зарегистрирован; выбор кода является допущением, поскольку исходные требования задают только тело ответа | JSON-объект с полем `id`, как в примере выше |
| `400` | Тело запроса недопустимо: отсутствует `topic`, отсутствует или пуст `checks`, нарушена структура элемента проверки, ожидаемое значение не является строкой либо `jsonPath` не соответствует разрешённому синтаксису | Единое тело ошибки, `INVALID_REQUEST` |
| `503` | Не удалось обеспечить готовность консюмера топика из-за отказа клиента Kafka или недоступности общего брокера | Единое тело ошибки, `KAFKA_UNAVAILABLE` |

### Особенности

- Если `autoDeleteSeconds` не задано, используется параметр `autoDeleteSlotsSeconds`, как установлено исходными требованиями. Правила конфигурации см. в [`configuration.md`](configuration.md).
- Регистрация и сопоставление выполняются по [ограничениям условий](#ограничения-условий-проверки); правила обработки пустых условий, нескольких результатов JSONPath и совпадений с несколькими проверками определены в [модели проверки](architecture.md#правило-совпадения).
- Срок слота не продлевается ни поступлением записей, ни операциями чтения, ни регистрацией ожиданий.
- Если создание консюмера завершилось отказом, слот не регистрируется и частичного состояния не остаётся; порядок отката описан в [`architecture.md`](architecture.md).

## Асинхронное ожидание записей

### Назначение

Ожидание момента, когда под проверку попадёт заданное число записей. Метод избавляет тест от синхронного опроса счётчика: ответ откладывается до выполнения условия или до истечения тайм-аута, а поток обработки запроса не блокируется.

### Метод и путь

`POST /api/v1/slots/{id}/checks/{index}/wait?n=NNNN&timeoutMs=ms`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота, полученный при регистрации |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

| Параметр | Тип | Обязательность | Значение по умолчанию | Ограничения | Назначение |
| --- | --- | --- | --- | --- | --- |
| `n` | целое | Нет | `1` | Больше или равно `1` | Требуемое число записей, попавших под проверку |
| `timeoutMs` | целое | Нет | Значение `defaultWaitSeconds`, переведённое из секунд в миллисекунды; допущение | Больше нуля; значение задаётся в миллисекундах | Предельное время ожидания |

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

При выполнении условия (`200`) и при истечении тайм-аута (`504`) тело ответа — пустой JSON-объект. Метод не возвращает накопленные записи; для их получения используется метод чтения.

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Условие выполнено: под проверку попало не менее `n` записей | `{}` |
| `504` | Условие не выполнено за отведённое время, тайм-аут истёк | `{}` |
| `409` | Слот удалён — вручную или по истечении `autoDeleteSeconds` — до завершения ожидания | Единое тело ошибки, `SLOT_DELETED` |
| `404` | Слот с указанным `id` отсутствует при обращении | Единое тело ошибки, `SLOT_NOT_FOUND` |
| `404` | Корректный неотрицательный целый `index` выходит за границы набора проверок существующего слота | Единое тело ошибки, `CHECK_NOT_FOUND` |
| `400` | Некорректная форма `index`; значения `n` или `timeoutMs` недопустимы: не являются целыми числами, `n` меньше `1`, `timeoutMs` не больше нуля | Единое тело ошибки, `INVALID_REQUEST` |
| `503` | Штатная остановка сервиса прервала незавершённое ожидание | Единое тело ошибки, `SERVICE_STOPPING` |

### Особенности

- Ответ откладывается до выполнения условия или истечения тайм-аута; поток обработки запроса не удерживается, блокирующих пауз и опроса счётчика не выполняется. Механизм отложенного завершения описан в [`architecture.md`](architecture.md).
- Если требуемое число записей уже накоплено, ответ возвращается без ожидания новых записей.
- Тайм-аут завершает ожидание результатом «тайм-аут» и не влияет на накопление: записи, пришедшие позже, остаются в слоте и доступны методам подсчёта и чтения.
- При отсутствии `timeoutMs` принято использовать `defaultWaitSeconds` с переводом секунд в миллисекунды. Правила конфигурации см. в [`configuration.md`](configuration.md). Связь параметра запроса с параметром конфигурации является допущением, отмеченным выше.
- Удаление слота во время ожидания завершает ожидание отдельным результатом «слот удалён», который преобразуется в ошибку конфликта состояния `409`. Тест должен трактовать `409` как прекращение наблюдения, а не как истечение времени: коды `504` и `409` различимы и означают разные события.
- При штатной остановке незавершённое ожидание завершается `503` с кодом `SERVICE_STOPPING`, если HTTP-соединение ещё открыто и допускает отправку ответа. Это не тайм-аут `504` и не удаление слота `409`; если соединение уже закрыто, HTTP-ответ не гарантируется. При аварийном завершении процесса структурированный ответ также не гарантируется.
- При конкуренции выполнения условия, тайм-аута, удаления слота и штатной остановки побеждает событие, первым зафиксировавшее завершение ожидания. Ответ формируется однократно и впоследствии не заменяется; при гонке условия и тайм-аута возможен `200` или `504`, а запись сохраняется до удаления слота или остановки сервиса. Внутренний механизм описан в [`architecture.md`](architecture.md).
- Обрыв связи уже работающего консюмера с общим брокером сам по себе не завершает ожидание кодом `503`: ранее накопленные записи сохраняются, а ожидание может завершиться по условию, тайм-ауту, удалению слота или остановке сервиса. Недоступность брокера не обещает поступления новых записей.
- Ожидание не изменяет накопление: записи продолжают собираться и после разрешения ожидания.
- Несколько ожиданий по одному слоту и одной проверке допустимы и завершаются независимо.
- До регистрации ожидания индекс проверяется по правилам раздела «Проверка индекса по операциям»: некорректная форма даёт `400`, корректный индекс вне границ — `404`.

## Подсчёт записей проверки

### Назначение

Получение текущего числа записей, попавших под проверку. Метод не ждёт новых записей и возвращает снимок счётчика на момент обработки запроса.

### Метод и путь

`GET /api/v1/slots/{id}/checks/{index}/count`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

| Поле | Тип | Назначение |
| --- | --- | --- |
| `count` | целое | Число записей, попавших под проверку с момента регистрации слота |

```json
{
  "count": 2
}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот и проверка существуют | JSON-объект с целочисленным полем `count`, как в примере выше |
| `404` | Слот с указанным `id` отсутствует — удалён вручную или по сроку | Единое тело ошибки, `SLOT_NOT_FOUND` |
| `404` | Некорректная форма `index` либо индекс выходит за границы набора проверок слота | Единое тело ошибки, `CHECK_NOT_FOUND` |

### Особенности

- Счётчик охватывает все подходящие записи; лимит выборки (`count`) применяется только при чтении записей.
- Счётчик не сбрасывается при завершении ожиданий и при операциях чтения; он включает и непредставимые записи согласно [правилам разделения сопоставления и представления](#сохранение-сопоставление-и-представление).
- После удаления слота накопленные записи и счётчики освобождаются, поэтому метод возвращает `404`.
- Операция синхронная: она не ожидает новых записей и завершается до возврата ответа.
- Некорректная форма индекса и выход за границы дают `404`, а не общий ответ проверки параметров `400`; порядок проверки задан в разделе «Проверка индекса по операциям».

## Чтение записей проверки

### Назначение

Получение записей, попавших под проверку, с постраничной выборкой. Метод возвращает снимок накопителя и не ожидает новых записей.

### Метод и путь

`GET /api/v1/slots/{id}/checks/{index}?offset=N&count=M`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

| Параметр | Тип | Обязательность | Значение по умолчанию | Ограничения | Назначение |
| --- | --- | --- | --- | --- | --- |
| `offset` | целое | Нет — допущение | `0` — допущение | Больше или равно нулю | Смещение (`offset`) — число записей, пропускаемых от начала накопленного списка |
| `count` | целое | Нет | `20` | Больше нуля | Лимит выборки (`count`) — максимальное число возвращаемых записей |

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

При успехе возвращается массив объектов в [представлении полученной записи](#представление-полученной-записи). Тело ответа — JSON; двоичное тело чтения не является поддерживаемым вариантом. Пустой результат возвращается пустым массивом. При непредставимой записи возвращается единое тело ошибки вместо всего массива по [правилам ниже](#непредставимая-запись-и-ответ-всей-страницы).

```json
[
  {
    "headers": [
      {
        "name": "correlationId",
        "value": "corr-123"
      }
    ],
    "key": {
      "type": "BINARY",
      "data": "b3JkZXItNDI="
    },
    "value": {
      "type": "JSON",
      "data": {
        "orderId": "42",
        "status": "COMPLETED"
      }
    }
  },
  {
    "headers": [
      {
        "name": "correlationId",
        "value": "corr-123"
      }
    ],
    "key": {
      "type": "BINARY",
      "data": "b3JkZXItNDM="
    },
    "value": {
      "type": "JSON",
      "data": {
        "orderId": "43",
        "status": "COMPLETED"
      }
    }
  }
]
```

Значение заголовка возвращается как UTF-8-строка без base64; ключ — base64 исходных байтов; значение — разобранный JSON.

Пустой результат:

```json
[]
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот и проверка существуют; все записи выбранной страницы представимы либо страница пуста | Массив записей в представлении полученной записи |
| `404` | Слот с указанным `id` отсутствует — удалён вручную или по сроку | Единое тело ошибки, `SLOT_NOT_FOUND` |
| `404` | Некорректная форма `index` либо индекс выходит за границы набора проверок слота | Единое тело ошибки, `CHECK_NOT_FOUND` |
| `400` | Значения `offset` или `count` недопустимы: не являются целыми числами, `offset` меньше нуля, `count` не больше нуля | Единое тело ошибки, `INVALID_REQUEST` |
| `500` | Хотя бы одна запись выбранной страницы непредставима по правилам чтения | Единое тело ошибки, `RECORD_NOT_REPRESENTABLE` |

### Непредставимая запись и ответ всей страницы

После проверки параметров, наличия слота и границ индекса по разделу «Проверка индекса по операциям» применяется следующий порядок:

1. Из текущего снимка исходного накопителя выбирается страница по `offset` и `count`. Смещение и лимит выборки относятся ко всем накопленным записям, а не к отфильтрованному списку представимых записей.
2. До отправки успешного ответа выполняется представление всех записей выбранной страницы. Любая причина непредставимости из раздела [«Представление полученной записи»](#представление-полученной-записи) приводит к отказу всей страницы.
3. При отказе возвращается `500` с кодом `RECORD_NOT_REPRESENTABLE` и единым JSON-телом ошибки. Частичный массив, пропуск записи, подстановка заглушки, сокращение страницы и добор следующих записей вместо непредставимых запрещены. Уже сформированная часть массива не отправляется.
4. Непредставимые записи вне выбранной страницы не влияют на ответ. Пустая страница возвращается с `200` и `[]`, даже если в накопителе есть непредставимые записи.
5. Успешное и ошибочное чтение не изменяют исходные данные, позиции записей, счётчик и ожидания. Повторное чтение той же страницы неизменного снимка снова даёт ту же ошибку; автоматического исправления или удаления нет. Клиент может явно выбрать другую страницу, но сервис сам непредставимые записи не обходит.

Пример тела ошибки страницы:

```json
{
  "code": "RECORD_NOT_REPRESENTABLE",
  "message": "Не удалось представить все записи выбранной страницы в формате чтения. Накопленные записи не изменены."
}
```

Выбран `500`, поскольку корректный запрос не может получить обещанное представление хранимых данных; это не ошибка входного запроса `400` и не отказ доступа к Kafka `503`. Отдельный машинный код отличает ожидаемое ограничение представления от непредвиденного `INTERNAL_ERROR`; дополнительных полей с исходными байтами или содержимым записи в ответе нет. Отказ всей страницы сохраняет соответствие смещения, лимита выборки и счётчика, не выдаёт неполный результат за полный и не расширяет JSON-ограниченный контракт.

### Особенности

- Порядок записей в ответе соответствует порядку их поступления из Kafka. При чтении из нескольких разделов топика абсолютный порядок не гарантируется, поскольку он определяется Kafka.
- Если `offset` превышает число накопленных записей, возвращается пустой массив.
- Если `offset + count` превышает число накопленных записей, выбираются все оставшиеся записи: выход лимита за конец списка сам по себе не является ошибкой. Успех чтения этой страницы зависит от представимости выбранных записей по правилам выше.
- Операция синхронная: она не ожидает новых записей и не изменяет накопитель. Для ожидания появления записей используется метод асинхронного ожидания.
- После удаления слота накопленные записи освобождаются, поэтому метод возвращает `404`.
- Отсутствующие данные и ошибки декодирования обрабатываются по разделу [«Представление полученной записи»](#представление-полученной-записи); ответ определяется [политикой всей выбранной страницы](#непредставимая-запись-и-ответ-всей-страницы).
- Исходный тип `STRING`, `BINARY` или `JSON`, заданный при публикации, в Kafka не сохраняется, поэтому по ответу чтения нельзя достоверно установить исходный тип. Пробелы и порядок полей JSON при сериализации также не гарантируются.
- Некорректная форма индекса и выход за границы дают `404`, в отличие от недопустимых параметров выборки с кодом `400`; порядок проверки задан в разделе «Проверка индекса по операциям».

## Удаление слота

### Назначение

Досрочное удаление ненужного слота до истечения `autoDeleteSeconds`. Удаление освобождает накопленные записи и прерывает незавершённые ожидания этого слота.

### Метод и путь

`DELETE /api/v1/slots/{id}`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

Тело успешного ответа — пустой JSON-объект.

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот существовал и удалён; накопленные записи освобождены, незавершённые ожидания прерваны | `{}` |
| `404` | Слот с указанным `id` отсутствует: удалён ранее вручную, удалён по истечении `autoDeleteSeconds` или никогда не существовал | Единое тело ошибки, `SLOT_NOT_FOUND` |

### Особенности

- Все незавершённые запросы ожидания по этому слоту прерываются и завершаются с кодом `409`; тест получает признак прекращения наблюдения, а не истечения времени.
- Удаление идемпотентно по своему результату: повторный запрос по уже удалённому слоту не является ошибкой состояния реестра и возвращает `404` как признак отсутствия слота. Повторное удаление не изменяет состояние и безопасно для повторов.
- Записи, полученные консюмером после удаления, в слот не попадают. Методы подсчёта и чтения по удалённому слоту возвращают `404`.
- Слот остаётся доступным после истечения `autoDeleteSeconds` до фактического автоматического удаления; после него действуют те же ответы, что и после ручного удаления. Механизм очистки и влияние удаления на консюмер описаны в [`architecture.md`](architecture.md).

### Формат тела ошибки

Утверждённое тело всех ошибочных ответов API, кроме тайм-аута ожидания `504`, — JSON-объект ровно с двумя обязательными строковыми полями. Поле `code` — стабильный машинный код причины; поле `message` — непустое безопасное описание на русском языке. Вложенного объекта ошибки и дополнительных полей нет. Ответ передаётся с `Content-Type: application/json`.

```json
{
  "code": "KAFKA_UNAVAILABLE",
  "message": "Не удалось завершить операцию Kafka. Фактическая доставка записи может быть неизвестна."
}
```

Тест должен различать ошибки по HTTP-коду и полю `code`, а не по точному тексту `message`: формулировка сообщения не является стабильным идентификатором. Сообщение не содержит стек вызовов, внутреннее исключение KafkaJS, адреса инфраструктуры или содержимое записи; технические подробности остаются в журнале. Ошибки проверки Fastify преобразуются в этот же формат с сохранением кодов конкретной операции.

| HTTP-код | `code` | Причина |
| --- | --- | --- |
| `400` | `INVALID_REQUEST` | Некорректный JSON, отсутствие обязательного поля, недопустимая структура или параметр запроса; некорректная форма индекса ожидания |
| `400` | `INVALID_RECORD_TYPE` | Недопустимое поле `type` или несоответствие полезных данных выбранному типу публикации |
| `400` | `INVALID_BASE64` | Строковые полезные данные `BINARY` не соответствуют правилам base64 |
| `400` | `TOPIC_NOT_ALLOWED` | Топик запрещён списком `publisherTopics` |
| `404` | `SLOT_NOT_FOUND` | Слот отсутствует при обращении |
| `404` | `CHECK_NOT_FOUND` | Проверка отсутствует; также некорректная форма индекса в операциях подсчёта и чтения |
| `409` | `SLOT_DELETED` | Удаление слота завершило ранее зарегистрированное ожидание |
| `503` | `KAFKA_UNAVAILABLE` | Отказ нативного клиента Kafka или общего брокера при публикации либо обеспечении готовности консюмера при регистрации слота |
| `503` | `SERVICE_STOPPING` | Штатная остановка завершила незавершённое ожидание |
| `500` | `RECORD_NOT_REPRESENTABLE` | Невозможно представить хотя бы одну запись выбранной страницы чтения; причины и поведение заданы в [политике страницы](#непредставимая-запись-и-ответ-всей-страницы) |
| `500` | `INTERNAL_ERROR` | Непредвиденный внутренний отказ при обработке любой операции; не подменяет известную ошибку представления; подробности регистрируются, а не выдаются клиенту |

Дополнительные коды утверждены по назначению: `400` обозначает ошибку входных данных, `503` — невозможность завершить операцию из-за Kafka или остановки сервиса, `500` — невозможность сформировать предусмотренный ответ. У `500` различаются известная непредставимость страницы (`RECORD_NOT_REPRESENTABLE`) и непредвиденный внутренний отказ (`INTERNAL_ERROR`); они не подменяют известную ошибку входа или Kafka. Существующие `404` для некорректного индекса подсчёта и чтения сохранены, хотя другие ошибки параметров дают `400`. Исходные `409` при удалении слота во время ожидания и `404` при удалении отсутствующего слота не изменены. `503` не является рекомендацией автоматически повторять публикацию: доставка может быть неизвестна.

Ответы публикации `201` и `202`, успешного ожидания `200`, удаления `200` и тайм-аута ожидания `504` по-прежнему содержат **ровно `{}`**: не пустую строку, не отсутствие тела, не `null` и не объект ошибки. `504` с `{}` остаётся исключением из единой схемы. Ответ регистрации содержит идентификатор, подсчёт — счётчик, чтение — массив согласно описанию методов.

### Проверка индекса по операциям

Корректная форма `index` — непустая десятичная запись неотрицательного целого числа из цифр `0–9`, точно представимого как безопасное целое JavaScript, не больше `9007199254740991`. Знак, пробелы, дробная часть, экспоненциальная запись и переполнение недопустимы. Индекс не округляется, не усекается и не заменяется значением по умолчанию. Для корректной формы отдельно проверяется наличие элемента в массиве `checks` слота.

| Операция | Некорректная форма, в том числе отрицательное, дробное, нечисловое или слишком большое значение | Корректный индекс вне границ существующего слота |
| --- | --- | --- |
| Ожидание | `400`, `INVALID_REQUEST`; ожидание не регистрируется | `404`, `CHECK_NOT_FOUND`; ожидание не регистрируется |
| Подсчёт | `404`, `CHECK_NOT_FOUND`; счётчик не читается | `404`, `CHECK_NOT_FOUND` |
| Чтение | `404`, `CHECK_NOT_FOUND`; снимок не читается | `404`, `CHECK_NOT_FOUND` |

Порядок проверок для этих трёх операций: форма индекса, остальные параметры запроса, наличие слота, границы индекса. Первая обнаруженная ошибка определяет ответ. При корректных параметрах отсутствие слота даёт `404` с `SLOT_NOT_FOUND`, а выход индекса за границы найденного слота — `404` с `CHECK_NOT_FOUND`. Различие кодов некорректной формы является контрактом операции и не должно теряться из-за общей проверки схемы Fastify. Отсутствующий сегмент пути не является значением индекса: такой URL не соответствует маршруту. Публикация, регистрация и удаление слота не принимают индекс проверки.

### Ограничения сервиса

Архитектурные ограничения первой версии и их обоснование приведены в [`architecture.md`](architecture.md). Для клиента API существенны следующие последствия:

- После перезапуска требуется заново зарегистрировать слот; прежние идентификаторы и накопленные результаты не восстанавливаются.
- Слот следует регистрировать до инициирования тестируемой операции: уже прошедшие записи не воспроизводятся.
- Работа с несколькими репликами не предусмотрена; целевая нагрузка — 10–50 запросов в секунду.
- В принятой архитектуре аутентификация и авторизация не предусмотрены, квоты и ограничение частоты запросов не применяются.

### Особенности асинхронного ожидания

- Единственный метод с отложенным ответом — `POST /api/v1/slots/{id}/checks/{index}/wait`. Остальные методы завершаются до возврата ответа и не зависят от будущих событий.
- Механизм неблокирующего ожидания описан в [`architecture.md`](architecture.md); внешний контракт метода приведён в разделе «Асинхронное ожидание записей» выше.
- Результаты зарегистрированного ожидания различимы кодами: `200` — условие выполнено, `504` — истёк тайм-аут, `409` — слот удалён, `503` с `SERVICE_STOPPING` — сервис штатно останавливается. Удаление и остановка не являются тайм-аутом; ответ не содержит накопленных записей.
- Тайм-аут не отменяет накопление: записи, пришедшие после `504`, остаются в слоте и доступны методам подсчёта и чтения.
- Ожидание по проверке не влияет на другие ожидания того же слота и на ожидания других слотов.
