## Общие сведения и правила контракта

### Базовый путь и формат обмена

- Базовый путь всех методов — `/api/v1`. Полные пути приведены в описании каждого метода.
- Обмен выполняется в формате JSON: запросы с телом передают `Content-Type: application/json`, ответы возвращаются с JSON-телом.
- Имена полей передаются в кодовом написании и регистрозависимы: `topic`, `headers`, `name`, `type`, `data`, `value`, `key`, `checks`, `values`, `jsonPath`, `autoDeleteSeconds`, `count`, `offset`, `ack`, `id`, `n`, `timeoutMs`. Переименование полей не допускается.
- Бинарные данные на границе JSON/HTTP представляются base64-строкой. В Kafka передаются исходные байты; base64 не является форматом хранения в топике.
- Идентификатор слота — строка. Индекс проверки — целое число, отсчёт начинается с нуля и соответствует позиции элемента в массиве `checks` запроса регистрации слота.
- Успешный ответ, не возвращающий данных, содержит тело `{}`. Ответ, возвращающий данные, содержит JSON-объект или массив объектов описанной структуры.
- Тело ответа определяется описанием конкретного метода. В частности, ответ ожидания с кодом `504` содержит `{}`, а не описание ошибки. Остальные ошибочные ответы имеют единую структуру из раздела «Формат тела ошибки»; пустой JSON-объект не заменяется отсутствующим телом.

### Источники и статус контракта

Внешний контракт сверяется с OpenAPI-спецификацией сервиса: `/api-docs`; интерфейс Swagger UI доступен по `/api-docs/swagger-ui`. Технические сведения о реализации маршрутов и подготовке OpenAPI вынесены в [инженерную спецификацию API](specs/api.md#формирование-openapi).

### Общая структура описания методов

Каждый метод описан по единому шаблону: назначение, метод и путь, параметры пути, параметры запроса, тело запроса, тело ответа, коды состояния, особенности. Обозначения `{name}`, `{id}` и `{index}` заменяются значениями параметров пути; `0/1` означает выбор одного значения `ack`, а `NNNN`, `ms`, `N` и `M` — значения параметров запроса. Это условные обозначения, а не буквальные значения в запросе; в тела JSON-примеров они не входят.

### Сводная таблица методов

| Метод | Путь | Назначение | Успешный код |
| --- | --- | --- | --- |
| `POST` | `/api/v1/topics/{name}/records` | Публикация записи в топик | `201` или `202` |
| `POST` | `/api/v1/slots` | Регистрация слота с набором проверок | `201` |
| `POST` | `/api/v1/slots/{id}/checks/{index}/wait` | Асинхронное ожидание записей под проверкой | `200` |
| `GET` | `/api/v1/slots/{id}/checks/{index}/count` | Подсчёт записей, попавших под проверку | `200` |
| `GET` | `/api/v1/slots/{id}/checks/{index}` | Чтение записей, попавших под проверку | `200` |
| `DELETE` | `/api/v1/slots/{id}` | Удаление слота до истечения `autoDeleteSeconds` | `200` |

### Рекомендуемая последовательность вызова

1. Зарегистрировать слот с проверками методом `POST /api/v1/slots` и сохранить полученный `id`.
2. Инициировать тестируемую операцию, при необходимости опубликовав запись методом `POST /api/v1/topics/{name}/records`.
3. Дождаться нужного числа записей методом `POST /api/v1/slots/{id}/checks/{index}/wait` либо проверить их количество методом `GET /api/v1/slots/{id}/checks/{index}/count`.
4. Прочитать накопленные записи методом `GET /api/v1/slots/{id}/checks/{index}`.
5. Удалить слот методом `DELETE /api/v1/slots/{id}`, если он больше не нужен.

Порядок шагов 1 и 2 важен для теста: слот наблюдает только записи, полученные после его регистрации. Консюмер начинает чтение с конца разделов топика, поэтому записи, пришедшие до открытия слота или за время, пока консюмер был закрыт, в слот не попадают. Внутренние причины описаны в [инженерной спецификации архитектуры](specs/architecture.md#принятые-архитектурные-решения).

## Формат `RecordDto`

`RecordDto` — структура записи в теле запроса публикации. Запись, полученная из Kafka, возвращается методом чтения в отдельном JSON-ограниченном представлении. Причина различия: Kafka хранит только байты и не сохраняет типовую метку из HTTP-запроса, поэтому входная типизированная модель и представление полученной записи описываются раздельно.

Исходная типовая метка при чтении не восстанавливается, поэтому представление чтения не является копией исходного запроса. При этом корректно представленный объект чтения может быть опубликован снова по правилам модели публикации: отсутствие `type` у заголовков покрывается типом по умолчанию `STRING`, а `value` с типом `JSON` допустимо для публикации. Побайтовое сохранение исходного JSON при такой повторной публикации не гарантируется, поскольку значение сериализуется заново.

### Модель публикации

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `headers` | массив объектов | Нет | Набор заголовков записи; при отсутствии запись передаётся без заголовков |
| `headers[].name` | строка | Да, если элемент задан | Имя заголовка; остаётся обычной строкой и не типизируется |
| `headers[].type` | строка, закрытый перечень `STRING`, `BINARY`, `JSON` | Нет | Тип полезных данных заголовка; при отсутствии применяется `STRING` |
| `headers[].value` | строка или JSON-данные | Да, если элемент задан | Полезные данные заголовка: строка для `STRING` и `BINARY`, JSON-данные для `JSON` |
| `key` | объект | Нет | Ключ записи; при отсутствии запись передаётся без ключа |
| `key.type` | строка, закрытый перечень `STRING`, `BINARY`, `JSON` | Нет | Тип ключа; при отсутствии применяется `STRING` |
| `key.data` | строка или JSON-данные | Да, если `key` задан | Полезные данные ключа: строка для `STRING` и `BINARY`, JSON-данные для `JSON` |
| `value` | объект | Да | Значение записи |
| `value.type` | строка, закрытый перечень `STRING`, `BINARY`, `JSON` | Нет | Тип значения; при отсутствии применяется `JSON` |
| `value.data` | строка или JSON-данные | Да | Полезные данные значения: строка для `STRING` и `BINARY`, JSON-данные для `JSON` |

### Правила преобразования в байты

- `STRING` передаёт текст как UTF-8 без JSON-кавычек; `JSON` сериализует JSON-данные один раз и кодирует результат в UTF-8; `BINARY` принимает каноническую base64-строку и передаёт декодированные исходные байты. Base64 применяется только на границе JSON/HTTP и не хранится в Kafka.
- Для `BINARY` допустим стандартный алфавит base64, длина строки должна быть кратна четырём, а завершающее дополнение `=` обязательно, когда требуется. Пробелы, переносы строк, URL-безопасный алфавит и неканонические завершающие биты отклоняются. Пустая строка обозначает пустые байты.
- Значение `type` по умолчанию применяется только при отсутствии поля: `STRING` для `key` и значений заголовков, `JSON` для `value`. Для типов, кроме `BINARY`, ожидаемая форма данных — строка для `STRING` и JSON-данные для `JSON`.
- Ошибочный тип или несовместимая форма данных дают `400`, `INVALID_RECORD_TYPE`; некорректная base64-строка даёт `400`, `INVALID_BASE64`. При ошибке запись не публикуется.
- При чтении исходные байты представляются по правилам раздела [«Представление полученной записи»](#представление-полученной-записи). Метка `type` в Kafka не сохраняется, а JSON сериализуется заново, поэтому пробелы и порядок исходных полей не гарантируются.

Точные проверки и шаги передачи байтов нативному клиенту описаны в [инженерной спецификации API](specs/api.md#передача-байтов-при-публикации).

### Форма типизированного заголовка

Для заголовка используется минимальная обратно совместимая по форме запись `{name, type, value}`:

- `name` — обычная строка, имя заголовка не типизируется;
- `type` — необязательное поле закрытого перечня `STRING`, `BINARY`, `JSON`; при отсутствии применяется `STRING`;
- `value` — полезные данные: JSON-данные для `JSON`, строка для `STRING` и `BINARY`.

Такая форма сохраняет существующее поле `headers[].value` и не вводит неоднозначное вложение `value.value`. Одновременная поддержка двух форм заголовка не предусмотрена.

### Представление полученной записи

| Поле | Тип | Назначение |
| --- | --- | --- |
| `headers` | массив объектов | Обязательное поле; при отсутствии заголовков возвращается `[]`, а не `null` и не отсутствие поля |
| `headers[].name` | строка | Имя заголовка |
| `headers[].value` | строка | Значение заголовка, полученное строгим декодированием его байтов как UTF-8; base64 не применяется |
| `key` | объект | Поле присутствует только при наличии ключа; отсутствующий ключ Kafka представлен отсутствием поля, а не `null` |
| `key.type` | строка | Всегда `BINARY`: обозначение способа представления произвольных байтов в JSON, а не исходного типа публикации |
| `key.data` | строка | Base64 исходных байтов ключа; пустые байты представлены пустой строкой и отличаются от отсутствующего ключа |
| `value` | объект | Обязательное поле успешно представленной записи; отсутствие значения Kafka не имеет успешного представления |
| `value.type` | строка | Всегда `JSON` |
| `value.data` | JSON-данные | JSON-значение любого вида, полученное разбором строго декодированных UTF-8-байтов значения, включая JSON-значение `null` |

- Произвольные байты существующего ключа представимы через base64; декодирование ключа как UTF-8 и разбор его как JSON не требуются.
- Пустые байты существующего заголовка представлены пустой строкой. Отсутствие всех заголовков отличается от существующего заголовка без значения: последнее не представимо строкой и является ошибкой представления, а не основанием удалить заголовок или заменить его значение пустой строкой.
- Отсутствующее значение Kafka, в том числе запись об удалении ключа в уплотняемом топике, не подменяется JSON-значением `null`. Байты JSON-текста `null` представимы как `value` с `type`, равным `JSON`, и `data`, равным `null`; отсутствие байтов значения — ошибка представления.
- Все значения заголовков и значение записи декодируются строго как UTF-8. Некорректные последовательности не заменяются символом замены; корректный символ U+FFFD, уже содержащийся в исходном тексте, сам по себе ошибкой не является.
- После строгого декодирования значение записи должно быть корректным JSON. Пустые байты, текст из одних пробельных символов и иной некорректный JSON являются ошибкой представления, а не пустым результатом чтения.
- Поддерживается только JSON UTF-8 для значения полученной записи; ни двоичное тело ответа, ни запасное представление значения или заголовков через base64, строку, `null` или специальный объект ошибки внутри записи не вводятся. Последствия ошибки определяет [политика всей страницы](#непредставимая-запись-и-ответ-всей-страницы).
- Исходный тип `STRING`, `BINARY` или `JSON`, указанный при публикации, в Kafka не сохраняется и при чтении не восстанавливается.

### Сохранение, сопоставление и представление

Сохранение исходных данных, сопоставление условий и представление записи при чтении — разные операции. Запись может соответствовать проверке, но оказаться непредставимой в ответе чтения; подсчёт и ожидание учитывают совпавшие записи независимо от их представимости. Подробности внутреннего накопления и семантики сопоставления приведены в [инженерной спецификации архитектуры](specs/architecture.md#накопление-и-порядок-записей).

### Пример: публикация значения типа `JSON`

```json
{
  "headers": [
    {
      "name": "correlationId",
      "value": "corr-123"
    },
    {
      "name": "binaryTrace",
      "type": "BINARY",
      "value": "dHJhY2UtNDI="
    }
  ],
  "key": {
    "type": "STRING",
    "data": "order-42"
  },
  "value": {
    "type": "JSON",
    "data": {
      "orderId": "42",
      "status": "CREATED"
    }
  }
}
```

У заголовка `correlationId` тип не задан, поэтому применяется `STRING`. Заголовок `binaryTrace` декодируется из base64 в байты `trace-42`. Ключ передаётся как UTF-8-байты текста `order-42`, значение — как UTF-8-байты сериализованного JSON.

### Пример: публикация значения типа `BINARY`

```json
{
  "headers": [],
  "key": {
    "type": "STRING",
    "data": "order-42"
  },
  "value": {
    "type": "BINARY",
    "data": "Zm9vYmFy"
  }
}
```

Значение `Zm9vYmFy` декодируется в байты `66 6f 6f 62 61 72` (`foobar`), а не в байты текста `Zm9vYmFy`.

### Пример: представление полученной записи

```json
{
  "headers": [
    {
      "name": "correlationId",
      "value": "corr-123"
    }
  ],
  "key": {
    "type": "BINARY",
    "data": "b3JkZXItNDI="
  },
  "value": {
    "type": "JSON",
    "data": {
      "orderId": "42",
      "status": "COMPLETED"
    }
  }
}
```

Заголовок представлен UTF-8-строкой без base64 и без поля `type`; ключ — base64 исходных байтов; значение — разобранный JSON.

Пример записи без ключа и заголовков, значение которой содержит JSON-текст `null`:

```json
{
  "headers": [],
  "value": {
    "type": "JSON",
    "data": null
  }
}
```

Этот пример не обозначает отсутствующее значение Kafka: оно непредставимо по правилам выше. Выбор отсутствующего поля для ключа и пустого массива для заголовков сохраняет совместимость с формой модели публикации без добавления вариантов с `null`.

## Публикация записей в топики

### Назначение

Передача записи в топик Kafka через сервис. Метод позволяет тесту инициировать асинхронную операцию без собственного клиента Kafka. Результат публикации не зависит от того, открыт ли слот по этому топику: попадание записи в слот проверяется только методами ожидания, подсчёта и чтения.

### Метод и путь

`POST /api/v1/topics/{name}/records?ack=0/1`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `name` | строка | Да | Имя топика, в который публикуется запись |

### Параметры запроса

| Параметр | Тип | Обязательность | Допустимые значения | Назначение |
| --- | --- | --- | --- | --- |
| `ack` | целое | Нет | `0`, `1`; значение по умолчанию `1` | Режим подтверждения отправки |

Значения `ack`:

| Значение | Смысл | Код успешного ответа |
| --- | --- | --- |
| `1` | Сервис дожидается подтверждения брокера и сообщает, что отправка подтверждена | `201` |
| `0` | Сервис не дожидается подтверждения брокера и сообщает, что сообщение принято к отправке | `202` |

### Тело запроса

Тело — объект модели публикации, описанной в разделе «Формат `RecordDto`». Обязательным является поле `value`; поля `headers` и `key` необязательны. Пример с полностью опущенными `type` показывает применение значений по умолчанию:

```json
{
  "headers": [
    {
      "name": "correlationId",
      "value": "corr-123"
    }
  ],
  "key": {
    "data": "order-42"
  },
  "value": {
    "data": {
      "orderId": "42",
      "status": "CREATED"
    }
  }
}
```

Здесь заголовок и ключ интерпретируются как `STRING`, значение — как `JSON`.

### Принятие отправки без подтверждения

При `ack=0` ответ `202` означает, что сервис принял запись к отправке, но не подтверждает её получение или сохранение брокером. Доставка, попадание записи в слот и сохранность после остановки или аварии сервиса не гарантируются. При отказе или разрыве соединения фактическая доставка может быть неизвестна; автоматический повтор запроса может привести к дубликату. Отказ, обнаруженный до принятия, возвращается как `503`, а поздний отказ после ответа не меняет уже отправленный ответ. Внутренняя граница принятия описана в [инженерной спецификации API](specs/api.md#граница-принятия-при-публикации-без-подтверждения).

### Тело ответа

Тело успешного ответа (`201` или `202`) — пустой JSON-объект. Ошибки возвращаются в едином формате из раздела «Формат тела ошибки».

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `201` | Отправка подтверждена брокером; возвращается при `ack=1` | `{}` |
| `202` | Сообщение принято к отправке без ожидания подтверждения брокера; возвращается при `ack=0` | `{}` |
| `400` | Список `publisherTopics` непуст и имя топика не соответствует ни одному его регулярному выражению | Единое тело ошибки, `TOPIC_NOT_ALLOWED` |
| `400` | Неизвестный или некорректный `type`, форма полезных данных не соответствует выбранному типу | Единое тело ошибки, `INVALID_RECORD_TYPE` |
| `400` | Полезные данные `BINARY` — строка с некорректной base64 | Единое тело ошибки, `INVALID_BASE64` |
| `400` | Недопустимые параметры или структура запроса, в том числе `ack` вне `0`, `1`, отсутствующее обязательное поле или некорректный JSON | Единое тело ошибки, `INVALID_REQUEST` |
| `503` | Отказ публикации или недоступность общего брокера: при `ack=1` подтверждение не получено, при `ack=0` отказ обнаружен до границы принятия | Единое тело ошибки, `KAFKA_UNAVAILABLE` |

### Особенности

- Допустимость топика определяется параметром `publisherTopics`; его правила описаны в [`configuration.md`](configuration.md).
- Тип задаётся закрытым перечнем `STRING`, `BINARY`, `JSON`. Значения по умолчанию применяются только при отсутствии `type`: `STRING` для `key` и значений заголовков, `JSON` для `value`. При неизвестном или некорректном `type`, несоответствии формы `data` выбранному типу или некорректной base64-строке для `BINARY` данные не публикуются и не заменяются значением по умолчанию: ошибочные данные не должны незаметно преобразовываться.
- Режим `ack` определяет, требуется ли подтверждение брокера; это не подтверждение накопления записи в слоте, и публикация не изменяет состав слотов или накопление записей.
- При `ack=1` отказ отправки, в том числе сетевой тайм-аут подтверждения, возвращает `503` с кодом `KAFKA_UNAVAILABLE`, а не `504` ожидания записей. Фактическая доставка может быть неизвестна. Для `ack=0` действует граница принятия, определённая выше.
- Метод не возвращает идентификатор слота и не содержит признака попадания записи в слот.
- Задержка между успешным ответом публикации и появлением записи в слоте определяется Kafka и сервисом не гарантируется; поэтому ожидание реализовано асинхронным с тайм-аутом.

## Регистрация слота и проверок

### Назначение

Создание слота — точки наблюдения за топиком. С момента регистрации слота начинают заполняться результаты его проверок: каждая полученная из топика запись сопоставляется с проверками слота, и подходящие записи накапливаются. Слот привязывается к одному топику и неизменяемому набору проверок; обычно слот регистрируется по идентификатору корреляции.

### Метод и путь

`POST /api/v1/slots`

### Параметры пути

Метод не имеет параметров пути.

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `topic` | строка | Да | Имя наблюдаемого топика |
| `autoDeleteSeconds` | целое, больше нуля | Нет | Срок автоматического удаления слота в секундах, отсчитываемый от момента регистрации |
| `checks` | непустой массив объектов | Да | Набор проверок слота; позиция элемента задаёт `index` в путях остальных методов |
| `checks[].headers` | массив объектов | Нет | Ожидаемые заголовки записи; пустой набор не накладывает ограничения |
| `checks[].headers[].name` | строка | Да, если элемент задан | Имя ожидаемого заголовка |
| `checks[].headers[].value` | строка | Да, если элемент задан | Ожидаемое значение заголовка — обычная UTF-8-строка, а не base64 |
| `checks[].values` | массив объектов | Нет | Ожидаемые значения, извлекаемые из значения записи по `jsonPath`; пустой набор не накладывает ограничения |
| `checks[].values[].jsonPath` | строка | Да, если элемент задан | Путь по [разрешённому синтаксису](#допустимый-синтаксис-jsonpath) внутри разобранного значения записи, а не объекта представления чтения |
| `checks[].values[].value` | строка | Да, если элемент задан | Ожидаемая строка по правилам преобразования результата из [инженерной спецификации архитектуры](specs/architecture.md#преобразование-и-сопоставление-результатов-jsonpath); не произвольные JSON-данные |

### Ограничения условий проверки

Условия одной проверки соединяются логическим И. Ожидаемые значения в `checks[].headers[].value` и `checks[].values[].value` должны быть строками; автоматическое приведение других JSON-типов к строке не выполняется. Пустая строка допустима. Повторяющиеся имена заголовков и пути `jsonPath` допустимы. Для ожидаемого заголовка поле `type` не задаётся.

При регистрации проверяется синтаксис всех путей. Недопустимый путь или нестроковое ожидаемое значение отклоняет весь запрос с `400`, `INVALID_REQUEST`; частичная регистрация не выполняется. Полная семантика сопоставления и преобразования значений описана в [инженерной спецификации архитектуры](specs/architecture.md#правило-совпадения).

### Допустимый синтаксис JSONPath

JSONPath (язык выбора узлов JSON) поддерживается только в следующем ограниченном виде, независимо от возможностей выбранной библиотеки. Путь начинается с `$`, обозначающего всё разобранное значение записи, и содержит ноль или более шагов из таблицы, соединённых без дополнительных разделителей. Пустая строка не является путём и отклоняется.

| Форма | Назначение | Пример пути |
| --- | --- | --- |
| `$` | Выбор корня; корнем может быть объект, массив или скаляр, включая `null` | `$` |
| `.имя` | Выбор собственного свойства объекта; имя начинается с латинской буквы или `_` и продолжается латинскими буквами, цифрами или `_` | `$.order.status` |
| `["имя"]` | Выбор собственного свойства объекта с произвольным именем; внутри скобок ровно одна строка в двойных кавычках по правилам JSON, включая стандартные экранирования | `$["order.id"]`, `$[""]`, `$["статус"]` |
| `[индекс]` | Выбор элемента массива; индекс — `0` либо десятичные цифры с первой цифрой `1–9`, не больше `9007199254740991` | `$.items[0].id` |
| `[*]` | Выбор всех непосредственных элементов массива или значений собственных свойств объекта | `$.items[*].id`, `$[*]` |

Пробелы вне строкового имени свойства запрещены, включая начальные и конечные; внутри такого имени пробелы являются частью имени. Индекс не содержит знака, ведущих нулей, дробной части или экспоненты. Скобочный выбор имени использует только двойные кавычки: одинарные кавычки не поддерживаются. Экранированное имя после разбора обозначает буквальное имя свойства, а не новый фрагмент пути; например, `$["a.b"]` выбирает одно свойство с точкой в имени. Выход индекса за границы массива корректен синтаксически, но не выбирает узел. Безопасный обход и защита от доступа к прототипам описаны в [инженерной спецификации архитектуры](specs/architecture.md#безопасное-вычисление-jsonpath).

Все остальные формы запрещены, в частности рекурсивный спуск, сокращённый выбор всех свойств через точку, объединения селекторов, срезы, отрицательные индексы, фильтры, регулярные выражения, вычисляемые индексы, обращения к текущему узлу, вызовы функций, арифметические и логические выражения, расширения типов и служебные операторы библиотеки. Например, `$..id`, `$.*`, `$['id']`, `$.items[0,1]`, `$.items[0:2]`, `$.items[-1]`, `$.items[?(@.id == 1)]` и `$.items[(@.length-1)]` отклоняются с `400`, `INVALID_REQUEST`, а не принимаются как условия, которые никогда не совпадут. Этот ограниченный синтаксис является пользовательским ограничением языка JSONPath.

### Пример регистрации

Пример запроса:

```json
{
  "topic": "orders.results",
  "autoDeleteSeconds": 300,
  "checks": [
    {
      "headers": [
        {
          "name": "correlationId",
          "value": "corr-123"
        }
      ],
      "values": [
        {
          "jsonPath": "$.status",
          "value": "COMPLETED"
        }
      ]
    },
    {
      "values": [
        {
          "jsonPath": "$.orderId",
          "value": "42"
        }
      ]
    }
  ]
}
```

В примере слот содержит две проверки: проверка с индексом `0` требует совпадения заголовка `correlationId` со строкой `corr-123` и значения `$.status`, проверка с индексом `1` — только значения `$.orderId`.

### Тело ответа

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | строка | Идентификатор созданного слота; используется во всех последующих методах работы со слотом |

```json
{
  "id": "3f6b1a2c-9d4e-4b7a-8c1a-2e5f7a9b0c3d"
}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `201` | Слот зарегистрирован | JSON-объект с полем `id`, как в примере выше |
| `400` | Тело запроса недопустимо: отсутствует `topic`, отсутствует или пуст `checks`, нарушена структура элемента проверки, ожидаемое значение не является строкой либо `jsonPath` не соответствует разрешённому синтаксису | Единое тело ошибки, `INVALID_REQUEST` |
| `503` | Не удалось обеспечить готовность наблюдения за топиком из-за отказа Kafka или недоступности общего брокера | Единое тело ошибки, `KAFKA_UNAVAILABLE` |

### Особенности

- Если `autoDeleteSeconds` не задано, применяется `autoDeleteSlotsSeconds`; пользовательские параметры и их значения описаны в [`configuration.md`](configuration.md).
- Срок слота не продлевается поступлением записей, чтением или регистрацией ожиданий.
- Если регистрация не может обеспечить готовность наблюдения за топиком, слот не создаётся и возвращается `503`, `KAFKA_UNAVAILABLE`. Внутренний откат и жизненный цикл консюмера описаны в [инженерной спецификации архитектуры](specs/architecture.md#состояния-консюмера-и-переходы).

## Асинхронное ожидание записей

### Назначение

Ожидание момента, когда под проверку попадёт заданное число записей. Метод избавляет тест от повторных запросов счётчика: ответ возвращается при выполнении условия или по истечении тайм-аута.

### Метод и путь

`POST /api/v1/slots/{id}/checks/{index}/wait?n=NNNN&timeoutMs=ms`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота, полученный при регистрации |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

| Параметр | Тип | Обязательность | Значение по умолчанию | Ограничения | Назначение |
| --- | --- | --- | --- | --- | --- |
| `n` | строка с целым числом | Нет | `1` | Неотрицательное безопасное целое не меньше `1` | Требуемое число записей, попавших под проверку |
| `timeoutMs` | строка с целым числом | Нет | Значение `defaultWaitSeconds`, переведённое из секунд в миллисекунды | Неотрицательное безопасное целое больше нуля; значение задаётся в миллисекундах | Предельное время ожидания |

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

При выполнении условия (`200`) и при истечении тайм-аута (`504`) тело ответа — пустой JSON-объект. Метод не возвращает накопленные записи; для их получения используется метод чтения.

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Условие выполнено: под проверку попало не менее `n` записей | `{}` |
| `504` | Условие не выполнено за отведённое время, тайм-аут истёк | `{}` |
| `409` | Слот удалён — вручную или по истечении `autoDeleteSeconds` — до завершения ожидания | Единое тело ошибки, `SLOT_DELETED` |
| `404` | Слот с указанным `id` отсутствует при обращении | Единое тело ошибки, `SLOT_NOT_FOUND` |
| `404` | Корректный неотрицательный целый `index` выходит за границы набора проверок существующего слота | Единое тело ошибки, `CHECK_NOT_FOUND` |
| `400` | Некорректная форма `index`; значения `n` или `timeoutMs` недопустимы: не являются целыми числами, `n` меньше `1`, `timeoutMs` не больше нуля | Единое тело ошибки, `INVALID_REQUEST` |
| `503` | Штатная остановка сервиса прервала незавершённое ожидание | Единое тело ошибки, `SERVICE_STOPPING` |

### Особенности

- Если требуемое число записей уже накоплено, ответ возвращается без ожидания новых записей.
- Истечение времени завершает только ожидание: позднее полученные записи остаются доступными для подсчёта и чтения.
- Удаление слота до завершения ожидания даёт `409`, а штатная остановка сервиса — `503` с кодом `SERVICE_STOPPING`; эти события отличаются от тайм-аута `504`.
- Обрыв связи консюмера с брокером сам по себе не завершает ожидание кодом `503`; поступление новых записей при этом не гарантируется.
- Несколько ожиданий по одной проверке допустимы и завершаются независимо. Внутренние гонки и устройство неблокирующего механизма описаны в [инженерной спецификации архитектуры](specs/architecture.md#модель-ожидания).
- Значение `timeoutMs` по умолчанию берётся из `defaultWaitSeconds`; см. [`configuration.md`](configuration.md).
- Для различий обработки формы `index` см. [проверку индекса по операциям](#проверка-индекса-по-операциям).

## Подсчёт записей проверки

### Назначение

Получение текущего числа записей, попавших под проверку. Метод не ждёт новых записей и возвращает снимок счётчика на момент обработки запроса.

### Метод и путь

`GET /api/v1/slots/{id}/checks/{index}/count`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

| Поле | Тип | Назначение |
| --- | --- | --- |
| `count` | целое | Число записей, попавших под проверку с момента регистрации слота |

```json
{
  "count": 2
}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот и проверка существуют | JSON-объект с целочисленным полем `count`, как в примере выше |
| `404` | Слот с указанным `id` отсутствует — удалён вручную или по сроку | Единое тело ошибки, `SLOT_NOT_FOUND` |
| `404` | Некорректная форма `index` либо индекс выходит за границы набора проверок слота | Единое тело ошибки, `CHECK_NOT_FOUND` |

### Особенности

- Счётчик охватывает все совпавшие записи, включая непредставимые при чтении; `count` применяется только к чтению.
- Счётчик не сбрасывается после ожиданий или чтения. После удаления слота он недоступен, и запрос возвращает `404`.
- Операция не ждёт новых записей. Некорректная форма `index` и выход за границы дают `404`; подробности приведены в [проверке индекса по операциям](#проверка-индекса-по-операциям).

## Чтение записей проверки

### Назначение

Получение записей, попавших под проверку, с постраничной выборкой. Метод возвращает накопленные на момент запроса записи и не ожидает новых.

### Метод и путь

`GET /api/v1/slots/{id}/checks/{index}?offset=N&count=M`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |

| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

### Тело запроса

Метод не имеет тела запроса.

```json
  {
    "headers": [
      {
        "name": "correlationId",
        "value": "corr-123"
      }
    ],
    "key": {
      "type": "BINARY",
      "data": "b3JkZXItNDM="

]
```

Значение заголовка возвращается как UTF-8-строка без base64; ключ — base64 исходных байтов; значение — разобранный JSON.

Пустой результат:

```json
[]
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот и проверка существуют; все записи выбранной страницы представимы либо страница пуста | Массив записей в представлении полученной записи |
| `404` | Слот с указанным `id` отсутствует — удалён вручную или по сроку | Единое тело ошибки, `SLOT_NOT_FOUND` |
| `404` | Некорректная форма `index` либо индекс выходит за границы набора проверок слота | Единое тело ошибки, `CHECK_NOT_FOUND` |
| `400` | Значения `offset` или `count` недопустимы: не являются целыми числами, `offset` меньше нуля, `count` не больше нуля | Единое тело ошибки, `INVALID_REQUEST` |
| `500` | Хотя бы одна запись выбранной страницы непредставима по правилам чтения | Единое тело ошибки, `RECORD_NOT_REPRESENTABLE` |

### Непредставимая запись и ответ всей страницы

Если хотя бы одна запись выбранной страницы не может быть представлена, весь ответ чтения завершается `500` с кодом `RECORD_NOT_REPRESENTABLE`. Частичный массив не возвращается; записи вне выбранной страницы не влияют на результат. Пустая страница возвращается как `200` с `[]`. Чтение не удаляет и не исправляет записи. Внутренний порядок получения снимка и представления страницы описан в [инженерной спецификации API](specs/api.md#представление-страницы-чтения).

Пример тела ошибки страницы:

```json
{
  "code": "RECORD_NOT_REPRESENTABLE",
  "message": "Не удалось представить все записи выбранной страницы в формате чтения. Накопленные записи не изменены."
}
```

### Особенности

- Порядок записей соответствует порядку поступления из Kafka; при нескольких разделах топика общий порядок не гарантируется.
- Если `offset` больше числа накопленных записей, возвращается `[]`. Если конец страницы выходит за пределы накопленных данных, возвращаются все оставшиеся записи.
- Операция не ожидает новых записей и не изменяет накопленные данные; после удаления слота возвращается `404`.
- Исходный `type` при чтении не восстанавливается. Формат представления описан в разделе [«Представление полученной записи»](#представление-полученной-записи).
- Некорректная форма `index` и выход за границы дают `404`, параметры `offset` и `count` проверяются с ответом `400`; см. [проверку индекса по операциям](#проверка-индекса-по-операциям).

## Удаление слота

### Назначение

Досрочное удаление ненужного слота до истечения `autoDeleteSeconds`. Удаление освобождает накопленные записи и прерывает незавершённые ожидания этого слота.

### Метод и путь

`DELETE /api/v1/slots/{id}`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

Тело успешного ответа — пустой JSON-объект.

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот существовал и удалён; накопленные записи освобождены, незавершённые ожидания прерваны | `{}` |
| `404` | Слот с указанным `id` отсутствует: удалён ранее вручную, удалён по истечении `autoDeleteSeconds` или никогда не существовал | Единое тело ошибки, `SLOT_NOT_FOUND` |

### Особенности

- Незавершённые ожидания по слоту завершаются с `409`; это прекращение наблюдения, а не тайм-аут.
- Повторное удаление отсутствующего слота возвращает `404`.
- После фактического удаления слота последующие записи не накапливаются в нём, а подсчёт и чтение возвращают `404`.
- Истечение `autoDeleteSeconds` само по себе не означает немедленную недоступность: пока слот фактически не удалён, он остаётся доступным. Внутренний общий путь удаления описан в [инженерной спецификации архитектуры](specs/architecture.md#что-происходит-при-удалении-слота).

### Формат тела ошибки

Утверждённое тело всех ошибочных ответов API, кроме тайм-аута ожидания `504`, — JSON-объект ровно с двумя обязательными строковыми полями. Поле `code` — стабильный машинный код причины; поле `message` — непустое безопасное описание на русском языке. Вложенного объекта ошибки и дополнительных полей нет. Ответ передаётся с `Content-Type: application/json`.

```json
{
  "code": "KAFKA_UNAVAILABLE",
  "message": "Не удалось завершить операцию Kafka. Фактическая доставка записи может быть неизвестна."
}
```

Тест должен различать ошибки по HTTP-коду и полю `code`, а не по точному тексту `message`: формулировка сообщения не является стабильным идентификатором. Сообщение не содержит стек вызовов, внутреннее исключение, адреса инфраструктуры или содержимое записи; технические подробности остаются в журнале.

| HTTP-код | `code` | Причина |
| --- | --- | --- |
| `400` | `INVALID_REQUEST` | Некорректный JSON, отсутствие обязательного поля, недопустимая структура или параметр запроса; некорректная форма индекса ожидания |
| `400` | `INVALID_RECORD_TYPE` | Недопустимое поле `type` или несоответствие полезных данных выбранному типу публикации |
| `400` | `INVALID_BASE64` | Строковые полезные данные `BINARY` не соответствуют правилам base64 |
| `400` | `TOPIC_NOT_ALLOWED` | Топик запрещён списком `publisherTopics` |
| `404` | `SLOT_NOT_FOUND` | Слот отсутствует при обращении |
| `404` | `CHECK_NOT_FOUND` | Проверка отсутствует; также некорректная форма индекса в операциях подсчёта и чтения |
| `409` | `SLOT_DELETED` | Удаление слота завершило ранее зарегистрированное ожидание |
| `503` | `KAFKA_UNAVAILABLE` | Отказ публикации или общего брокера при публикации либо обеспечении готовности наблюдения при регистрации слота |
| `503` | `SERVICE_STOPPING` | Штатная остановка завершила незавершённое ожидание |
| `500` | `RECORD_NOT_REPRESENTABLE` | Невозможно представить хотя бы одну запись выбранной страницы чтения; причины и поведение заданы в [политике страницы](#непредставимая-запись-и-ответ-всей-страницы) |
| `500` | `INTERNAL_ERROR` | Непредвиденный внутренний отказ при обработке любой операции; не подменяет известную ошибку представления; подробности регистрируются, а не выдаются клиенту |

Дополнительные коды утверждены по назначению: `400` обозначает ошибку входных данных, `503` — невозможность завершить операцию из-за Kafka или остановки сервиса, `500` — невозможность сформировать предусмотренный ответ. У `500` различаются известная непредставимость страницы (`RECORD_NOT_REPRESENTABLE`) и непредвиденный внутренний отказ (`INTERNAL_ERROR`); они не подменяют известную ошибку входа или Kafka. Существующие `404` для некорректного индекса подсчёта и чтения сохранены, хотя другие ошибки параметров дают `400`. Исходные `409` при удалении слота во время ожидания и `404` при удалении отсутствующего слота не изменены. `503` не является рекомендацией автоматически повторять публикацию: доставка может быть неизвестна.

Ответы публикации `201` и `202`, успешного ожидания `200`, удаления `200` и тайм-аута ожидания `504` по-прежнему содержат **ровно `{}`**: не пустую строку, не отсутствие тела, не `null` и не объект ошибки. `504` с `{}` остаётся исключением из единой схемы. Ответ регистрации содержит идентификатор, подсчёт — счётчик, чтение — массив согласно описанию методов.

### Проверка индекса по операциям

`index` должен быть десятичным неотрицательным целым без знака, пробелов, ведущих нулей (кроме `0`), дробной или экспоненциальной части. Допустимый диапазон — от `0` до `9007199254740991`. Корректный индекс должен также соответствовать существующей позиции в `checks` слота.

| Операция | Некорректная форма `index` | Корректный индекс вне границ существующего слота |
| --- | --- | --- |
| Ожидание | `400`, `INVALID_REQUEST` | `404`, `CHECK_NOT_FOUND` |
| Подсчёт | `404`, `CHECK_NOT_FOUND` | `404`, `CHECK_NOT_FOUND` |
| Чтение | `404`, `CHECK_NOT_FOUND` | `404`, `CHECK_NOT_FOUND` |

Отсутствующий слот при корректных остальных параметрах даёт `404`, `SLOT_NOT_FOUND`. Для ожидания сначала проверяются `index`, затем `n` и `timeoutMs`; для чтения — `index`, затем `offset` и `count`. Поэтому первая ошибка параметров определяет ответ. Отсутствующий сегмент пути не является значением `index` и не соответствует маршруту.

### Особенности асинхронного ожидания

- Единственный метод с отложенным ответом — `POST /api/v1/slots/{id}/checks/{index}/wait`. Остальные методы завершаются до возврата ответа и не зависят от будущих событий.
- Механизм неблокирующего ожидания описан в [инженерной спецификации архитектуры](specs/architecture.md#модель-ожидания); внешний контракт метода приведён в [разделе ожидания](#асинхронное-ожидание-записей).
- Результаты зарегистрированного ожидания различимы кодами: `200` — условие выполнено, `504` — истёк тайм-аут, `409` — слот удалён, `503` с `SERVICE_STOPPING` — сервис штатно останавливается. Удаление и остановка не являются тайм-аутом; ответ не содержит накопленных записей.
- Тайм-аут не отменяет накопление: записи, пришедшие после `504`, остаются в слоте и доступны методам подсчёта и чтения.
- Ожидание по проверке не влияет на другие ожидания того же слота и на ожидания других слотов.
