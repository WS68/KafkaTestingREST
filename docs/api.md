# API

Документ описывает внешний контракт HTTP API: назначение методов, пути, параметры, тела запросов и ответов, коды состояний, ограничения и особенности асинхронного ожидания. Внутреннее устройство компонентов и обработка записей описываются в [`architecture.md`](architecture.md), а параметры конфигурации и их влияние — в [`configuration.md`](configuration.md). Назначение проекта, требования к запуску и инструкции по сборке остаются в [`../readme.md`](../readme.md); правила документирования определены в [`../AGENTS.md`](../AGENTS.md).

Состав документа:

- Общие сведения и правила контракта
- Формат `RecordDto`
- Публикация записей в топики
- Регистрация слота и проверок
- Асинхронное ожидание записей
- Подсчёт записей проверки
- Чтение записей проверки
- Удаление слота
- OpenAPI и Swagger UI
- Ошибки, ограничения и особенности ответов

## Общие сведения и правила контракта

### Базовый путь и формат обмена

- Базовый путь всех методов — `/api/v1`. Полные пути приведены в описании каждого метода.
- Обмен выполняется в формате JSON: запросы с телом передают `Content-Type: application/json`, ответы возвращаются с JSON-телом.
- Имена полей передаются в кодовом написании и регистрозависимы: `topic`, `headers`, `key`, `value`, `checks`, `values`, `jsonPath`, `autoDeleteSeconds`, `count`, `offset`, `ack`, `id`, `n`, `timeoutMs`. Переименование полей не допускается.
- Идентификатор слота — строка. Индекс проверки — целое число, отсчёт начинается с нуля и соответствует позиции элемента в массиве `checks` запроса регистрации слота.
- Успешный ответ, не возвращающий данных, содержит тело `{}`. Ответ, возвращающий данные, содержит JSON-объект или массив объектов описанной структуры.
- Ошибочный ответ содержит код состояния из диапазона `4xx` или `5xx` и JSON-объект с текстовым описанием ошибки. Гарантированной частью контракта является код состояния; полная структура тела ошибки и перечень кодов фиксируются в OpenAPI-спецификации, доступной по `/api-docs`, и должны совпадать с фактической реализацией.

### Общая структура описания методов

Каждый метод описан по единому шаблону: назначение, метод и путь, параметры пути, параметры запроса, тело запроса, тело ответа, коды состояния, особенности. Параметры-заполнители (`{name}`, `{id}`, `{index}`, `NNNN`, `ms`) используются только в описании путей и в таблицах параметров и никогда не входят в тела JSON-примеров.

### Сводная таблица методов

| Метод | Путь | Назначение | Успешный код |
| --- | --- | --- | --- |
| `POST` | `/api/v1/topics/{name}/records` | Публикация записи в топик через Kafka REST API | `201` или `202` |
| `POST` | `/api/v1/slots` | Регистрация слота с набором проверок | `201` |
| `POST` | `/api/v1/slots/{id}/checks/{index}/wait` | Асинхронное ожидание записей под проверкой | `200` |
| `GET` | `/api/v1/slots/{id}/checks/{index}/count` | Подсчёт записей, попавших под проверку | `200` |
| `GET` | `/api/v1/slots/{id}/checks/{index}` | Чтение записей, попавших под проверку | `200` |
| `DELETE` | `/api/v1/slots/{id}` | Удаление слота до истечения `autoDeleteSeconds` | `200` |

### Рекомендуемая последовательность вызова

1. Зарегистрировать слот с проверками методом `POST /api/v1/slots` и сохранить полученный `id`.
2. Инициировать тестируемую операцию, при необходимости опубликовав запись методом `POST /api/v1/topics/{name}/records`.
3. Дождаться нужного числа записей методом `POST /api/v1/slots/{id}/checks/{index}/wait` либо проверить их количество методом `GET /api/v1/slots/{id}/checks/{index}/count`.
4. Прочитать накопленные записи методом `GET /api/v1/slots/{id}/checks/{index}`.
5. Удалить слот методом `DELETE /api/v1/slots/{id}`, если он больше не нужен.

Порядок шагов 1 и 2 важен для теста: слот наблюдает только записи, полученные после его регистрации. Почему это так, описано в [`architecture.md`](architecture.md).

### Границы документа

Документ фиксирует только внешний контракт. Механизмы блокировок, жизненный цикл слотов и консюмеров, правила маршрутизации записей и фоновую очистку описывает [`architecture.md`](architecture.md). Значения параметров конфигурации, их типы и значения по умолчанию описывает [`configuration.md`](configuration.md); в этом документе параметры упоминаются только по имени и только там, где определяют поведение метода.

## Формат `RecordDto`

`RecordDto` — единая структура записи, используемая и в теле запроса публикации, и в элементах ответа чтения записей проверки. Одна и та же структура описывает запись на входе и на выходе, поэтому тест может повторно использовать полученный объект для публикации.

### Поля

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `headers` | массив объектов | Нет | Набор заголовков записи; при отсутствии запись передаётся без заголовков |
| `headers[].name` | строка | Да, если элемент задан | Имя заголовка |
| `headers[].value` | строка | Да, если элемент задан | Значение заголовка в кодировке base64 |
| `key` | объект | Нет | Ключ записи; при отсутствии запись передаётся без ключа |
| `key.type` | строка | Да, если `key` задан | Тип ключа: `BINARY` — двоичные данные |
| `key.data` | строка | Да, если `key` задан | Данные ключа в кодировке base64 |
| `value` | объект | Да | Значение записи |
| `value.type` | строка | Да | Тип значения: `JSON` — JSON-объект, `BINARY` — двоичные данные |
| `value.data` | объект или строка | Да | Для `value.type` = `JSON` — JSON-объект; для `value.type` = `BINARY` — строка в кодировке base64 |

### Правила представления

- Значения заголовков и данные ключа передаются строками в кодировке base64. Это относится к обеим сторонам контракта: и к публикуемой записи, и к записи, прочитанной из проверки.
- Для `value.type` = `JSON` поле `value.data` содержит JSON-объект и передаётся без экранирования в строку; сервис не изменяет структуру значения.
- Для `value.type` = `BINARY` поле `value.data` содержит строку base64, а не вложенный объект.
- Значения, извлечённые по `jsonPath` при проверке, вычисляются только по значению типа `JSON`.
- Запись передаётся в топик без изменения семантики заголовков, ключа и значения; преобразование типов и обогащение полей не выполняются.

### Пример: значение типа `JSON`

```json
{
  "headers": [
    {
      "name": "Header-1",
      "value": "SGVhZGVyLTE="
    },
    {
      "name": "Header-2",
      "value": "SGVhZGVyLTI="
    }
  ],
  "key": {
    "type": "BINARY",
    "data": "Zm9vYmFy"
  },
  "value": {
    "type": "JSON",
    "data": {
      "foo": "bar"
    }
  }
}
```

В примере значение заголовка `Header-1` — base64-строка `SGVhZGVyLTE=`, ключ `foobar` — base64-строка `Zm9vYmFy`, значение — JSON-объект.

### Пример: значение типа `BINARY`

```json
{
  "headers": [],
  "key": {
    "type": "BINARY",
    "data": "Zm9vYmFy"
  },
  "value": {
    "type": "BINARY",
    "data": "eyJmb28iOiJiYXIifQ=="
  }
}
```

## Публикация записей в топики

### Назначение

Передача записи в топик Kafka через Kafka REST API. Метод позволяет тесту инициировать асинхронную операцию без собственного клиента Kafka. Результат публикации не зависит от того, открыт ли слот по этому топику: попадание записи в слот проверяется только методами ожидания, подсчёта и чтения.

### Метод и путь

`POST /api/v1/topics/{name}/records?ack=0/1`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `name` | строка | Да | Имя топика, в который публикуется запись |

### Параметры запроса

| Параметр | Тип | Обязательность | Допустимые значения | Назначение |
| --- | --- | --- | --- | --- |
| `ack` | целое | Нет | `0`, `1`; при отсутствии используется `1` | Режим подтверждения отправки |

Значения `ack`:

| Значение | Смысл | Код успешного ответа |
| --- | --- | --- |
| `1` | Сервис дожидается подтверждения брокера и сообщает, что отправка подтверждена | `201` |
| `0` | Сервис не дожидается подтверждения брокера и сообщает, что сообщение принято к отправке | `202` |

### Тело запроса

Тело — объект `RecordDto`, описанный в разделе «Формат `RecordDto`». Обязательным является поле `value`; поля `headers` и `key` необязательны.

```json
{
  "headers": [
    {
      "name": "correlationId",
      "value": "Y29yci0xMjM="
    }
  ],
  "key": {
    "type": "BINARY",
    "data": "b3JkZXItNDI="
  },
  "value": {
    "type": "JSON",
    "data": {
      "orderId": "42",
      "status": "CREATED"
    }
  }
}
```

### Тело ответа

Тело ответа — пустой JSON-объект.

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `201` | Отправка подтверждена брокером; возвращается при `ack=1` | `{}` |
| `202` | Сообщение принято к отправке без ожидания подтверждения брокера; возвращается при `ack=0` | `{}` |
| `400` | Топик недопустим: имя не соответствует ни одному регулярному выражению из `publisherTopics` | JSON-объект с описанием ошибки |

### Особенности

- Допустимость топика проверяется по списку `publisherTopics` до обращения к Kafka: при недопустимом топике сетевой вызов не выполняется, ответ `400` формируется без участия брокера. Правила сопоставления и поведение пустого списка описаны в [`configuration.md`](configuration.md).
- Режим `ack` влияет только на то, дожидается ли сервис подтверждения брокера; на состав слотов и накопление записей публикация не влияет.
- При недоступности Kafka REST API ответ не является успешным; конкретный код состояния фиксируется в OpenAPI-спецификации по `/api-docs`. Повторных попыток, очередей и фоновой досылки нет, поэтому тест должен трактовать любой ответ вне диапазона `2xx` как отказ публикации.
- Метод не возвращает идентификатор слота и не содержит признака попадания записи в слот.
- Задержка между успешным ответом публикации и появлением записи в слоте определяется Kafka и сервисом не гарантируется; поэтому ожидание реализовано асинхронным с тайм-аутом.

## Регистрация слота и проверок

### Назначение

Создание слота — точки наблюдения за топиком. С момента регистрации слота начинают заполняться результаты его проверок: каждая полученная из топика запись сопоставляется с проверками слота, и подходящие записи накапливаются. Слот привязывается к одному топику и неизменяемому набору проверок; обычно слот регистрируется по идентификатору корреляции.

### Метод и путь

`POST /api/v1/slots`

### Параметры пути

Метод не имеет параметров пути.

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `topic` | строка | Да | Имя наблюдаемого топика |
| `autoDeleteSeconds` | целое, больше нуля | Нет | Срок автоматического удаления слота в секундах, отсчитываемый от момента регистрации |
| `checks` | массив объектов | Да | Набор проверок слота; позиция элемента задаёт `index` в путях остальных методов |
| `checks[].headers` | массив объектов | Нет | Ожидаемые заголовки записи; пустой набор не накладывает ограничения |
| `checks[].headers[].name` | строка | Да, если элемент задан | Имя ожидаемого заголовка |
| `checks[].headers[].value` | строка | Да, если элемент задан | Ожидаемое значение заголовка в base64, в том же представлении, в котором значение передаётся в `RecordDto` |
| `checks[].values` | массив объектов | Нет | Ожидаемые значения, извлекаемые из значения записи по `jsonPath`; пустой набор не накладывает ограничения |
| `checks[].values[].jsonPath` | строка | Да, если элемент задан | Путь к значению внутри значения записи типа `JSON` |
| `checks[].values[].value` | строка | Да, если элемент задан | Ожидаемое значение, сравниваемое как строка |

Пример запроса:

```json
{
  "topic": "orders.results",
  "autoDeleteSeconds": 300,
  "checks": [
    {
      "headers": [
        {
          "name": "correlationId",
          "value": "Y29yci0xMjM="
        }
      ],
      "values": [
        {
          "jsonPath": "$.status",
          "value": "COMPLETED"
        }
      ]
    },
    {
      "values": [
        {
          "jsonPath": "$.orderId",
          "value": "42"
        }
      ]
    }
  ]
}
```

В примере слот содержит две проверки: проверка с индексом `0` требует совпадения заголовка `correlationId` и значения `$.status`, проверка с индексом `1` — только значения `$.orderId`.

### Тело ответа

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | строка | Идентификатор созданного слота; используется во всех последующих методах работы со слотом |

```json
{
  "id": "3f6b1a2c-9d4e-4b7a-8c1a-2e5f7a9b0c3d"
}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `201` | Слот зарегистрирован | `{ "id": ... }` |
| `400` | Тело запроса недопустимо: отсутствует `topic`, отсутствует или пуст `checks`, нарушена структура элемента проверки | JSON-объект с описанием ошибки |
| `503` | Не удалось создать консюмер топика: клиент Kafka не инициализирован или подписка не выполнена | JSON-объект с описанием ошибки |

### Особенности

- Срок автоматического удаления вычисляется один раз в момент регистрации слота: используется `autoDeleteSeconds` из запроса, а если поле не задано — значение параметра `autoDeleteSlotsSeconds`. Явно заданный срок имеет приоритет; значения по умолчанию и правило приоритета описаны в [`configuration.md`](configuration.md).
- Запись удовлетворяет проверке только при совпадении **всех** её параметров: каждого ожидаемого заголовка и каждого значения, извлечённого по `jsonPath`. Несовпадение хотя бы одного параметра означает, что запись в эту проверку не попадает; частичного накопления не существует.
- Пустой набор `headers` или пустой набор `values` не накладывает ограничения по этой части проверки. Проверка без обоих наборов удовлетворяется любой записью топика.
- Ошибка вычисления `jsonPath` (отсутствующий путь, неразбираемое значение) трактуется как несовпадение, а не как ошибка запроса или отказа обработки.
- Одна запись может одновременно попасть в несколько проверок одного слота и в проверки нескольких слотов; копии накапливаются независимо.
- Срок слота не продлевается ни поступлением записей, ни операциями чтения, ни регистрацией ожиданий.
- Если создание консюмера завершилось отказом, слот не регистрируется и частичного состояния не остаётся; порядок отката описан в [`architecture.md`](architecture.md).

## Асинхронное ожидание записей

### Назначение

Ожидание момента, когда под проверку попадёт заданное число записей. Метод избавляет тест от синхронного опроса счётчика: ответ откладывается до выполнения условия или до истечения тайм-аута, а поток обработки запроса не блокируется.

### Метод и путь

`POST /api/v1/slots/{id}/checks/{index}/wait?n=NNNN&timeoutMs=ms`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота, полученный при регистрации |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

| Параметр | Тип | Обязательность | Значение по умолчанию | Ограничения | Назначение |
| --- | --- | --- | --- | --- | --- |
| `n` | целое | Нет | `1` | Больше или равно `1` | Требуемое число записей, попавших под проверку |
| `timeoutMs` | целое | Нет | Определяется параметром `defaultWaitSeconds` | Больше нуля; значение задаётся в миллисекундах | Предельное время ожидания |

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

Тело успешного ответа — пустой JSON-объект.

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Условие выполнено: под проверку попало не менее `n` записей | `{}` |
| `504` | Условие не выполнено за отведённое время, тайм-аут истёк | `{}` |
| `409` | Слот удалён — вручную или по истечении `autoDeleteSeconds` — до завершения ожидания | JSON-объект с описанием ошибки |
| `404` | Слот с указанным `id` отсутствует либо `index` выходит за границы набора проверок слота | JSON-объект с описанием ошибки |
| `400` | Значения `n` или `timeoutMs` недопустимы: не являются целыми числами, `n` меньше `1`, `timeoutMs` не больше нуля | JSON-объект с описанием ошибки |

### Особенности

- Ответ откладывается до выполнения условия или истечения тайм-аута; поток обработки запроса не удерживается, блокирующих пауз и опроса счётчика не выполняется. Механизм отложенного завершения описан в [`architecture.md`](architecture.md).
- Условие проверяется сразу при регистрации ожидания: если требуемое число записей уже накоплено, ответ возвращается без задержки и без взведения таймера.
- Тайм-аут завершает ожидание результатом «тайм-аут» и не влияет на накопление: записи, пришедшие позже, остаются в слоте и доступны методам подсчёта и чтения.
- Значение по умолчанию для `timeoutMs` берётся из параметра `defaultWaitSeconds`; тип, значение по умолчанию и правила применения параметра описаны в [`configuration.md`](configuration.md). Если параметр не задан и в запросе, применяется значение по умолчанию.
- Удаление слота во время ожидания завершает ожидание отдельным результатом «слот удалён», который преобразуется в ошибку конфликта состояния `409`. Тест должен трактовать `409` как прекращение наблюдения, а не как истечение времени: коды `504` и `409` различимы и означают разные события.
- Если условие выполняется одновременно с истечением тайм-аута, ожидание завершается ровно один раз результатом того события, которое первым зафиксировало завершение; ответ формируется однократно. Запись при этом остаётся в слоте.
- Ожидание не изменяет накопление: записи продолжают собираться и после разрешения ожидания.
- Несколько ожиданий по одному слоту и одной проверке допустимы и завершаются независимо.

## Подсчёт записей проверки

### Назначение

Получение текущего числа записей, попавших под проверку. Метод не ждёт новых записей и возвращает снимок счётчика на момент обработки запроса.

### Метод и путь

`GET /api/v1/slots/{id}/checks/{index}/count`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

| Поле | Тип | Назначение |
| --- | --- | --- |
| `count` | целое | Число записей, попавших под проверку с момента регистрации слота |

```json
{
  "count": 2
}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот и проверка существуют | `{ "count": ... }` |
| `404` | Слот с указанным `id` отсутствует — удалён вручную или по сроку | JSON-объект с описанием ошибки |
| `404` | `index` выходит за границы набора проверок слота или не является целым числом | JSON-объект с описанием ошибки |

### Особенности

- Счётчик охватывает все подходящие записи без ограничения количества; лимит применяется только при чтении записей.
- Счётчик не сбрасывается при завершении ожиданий и при операциях чтения.
- После удаления слота накопленные записи и счётчики освобождаются, поэтому метод возвращает `404`.
- Операция синхронная: она не ожидает новых записей и завершается до возврата ответа.

## Чтение записей проверки

### Назначение

Получение записей, попавших под проверку, с постраничной выборкой. Метод возвращает снимок накопителя и не ожидает новых записей.

### Метод и путь

`GET /api/v1/slots/{id}/checks/{index}?offset=N&count=M`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

| Параметр | Тип | Обязательность | Значение по умолчанию | Ограничения | Назначение |
| --- | --- | --- | --- | --- | --- |
| `offset` | целое | Нет | `0` | Больше или равно нулю | Смещение (`offset`) — число записей, пропускаемых от начала накопленного списка |
| `count` | целое | Нет | `20` | Больше нуля | Лимит выборки (`count`) — максимальное число возвращаемых записей |

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

Массив объектов `RecordDto`, описанных в разделе «Формат `RecordDto`». Пустой результат возвращается пустым массивом.

```json
[
  {
    "headers": [
      {
        "name": "correlationId",
        "value": "Y29yci0xMjM="
      }
    ],
    "key": {
      "type": "BINARY",
      "data": "b3JkZXItNDI="
    },
    "value": {
      "type": "JSON",
      "data": {
        "orderId": "42",
        "status": "COMPLETED"
      }
    }
  },
  {
    "headers": [
      {
        "name": "correlationId",
        "value": "Y29yci0xMjM="
      }
    ],
    "key": {
      "type": "BINARY",
      "data": "b3JkZXItNDM="
    },
    "value": {
      "type": "JSON",
      "data": {
        "orderId": "43",
        "status": "COMPLETED"
      }
    }
  }
]
```

Пустой результат:

```json
[]
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот и проверка существуют | Массив `RecordDto` |
| `404` | Слот с указанным `id` отсутствует — удалён вручную или по сроку | JSON-объект с описанием ошибки |
| `404` | `index` выходит за границы набора проверок слота или не является целым числом | JSON-объект с описанием ошибки |
| `400` | Значения `offset` или `count` недопустимы: не являются целыми числами, `offset` меньше нуля, `count` не больше нуля | JSON-объект с описанием ошибки |

### Особенности

- Порядок записей в ответе соответствует порядку их поступления из Kafka. При чтении из нескольких разделов топика абсолютный порядок не гарантируется, поскольку он определяется Kafka.
- Если `offset` превышает число накопленных записей, возвращается пустой массив.
- Если `offset + count` превышает число накопленных записей, возвращаются все оставшиеся записи без ошибки.
- Операция синхронная: она не ожидает новых записей и не изменяет накопитель. Для ожидания появления записей используется метод асинхронного ожидания.
- После удаления слота накопленные записи освобождаются, поэтому метод возвращает `404`.

## Удаление слота

### Назначение

Досрочное удаление ненужного слота до истечения `autoDeleteSeconds`. Удаление освобождает накопленные записи и прерывает незавершённые ожидания этого слота.

### Метод и путь

`DELETE /api/v1/slots/{id}`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

Тело успешного ответа — пустой JSON-объект.

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот существовал и удалён; накопленные записи освобождены, незавершённые ожидания прерваны | `{}` |
| `404` | Слот с указанным `id` отсутствует: удалён ранее вручную, удалён по истечении `autoDeleteSeconds` или никогда не существовал | JSON-объект с описанием ошибки |

### Особенности

- Все незавершённые запросы ожидания по этому слоту прерываются и завершаются с кодом `409`; тест получает признак прекращения наблюдения, а не истечения времени.
- Удаление идемпотентно по своему результату: повторный запрос по уже удалённому слоту не является ошибкой состояния реестра и возвращает `404` как признак отсутствия слота. Повторное удаление не изменяет состояние и безопасно для повторов.
- Записи, полученные консюмером после удаления, в слот не попадают. Методы подсчёта и чтения по удалённому слоту возвращают `404`.
- Удаление по сроку и удаление по запросу используют один и тот же путь удаления, поэтому поведение ожиданий и накопленных записей идентично; удаление по сроку выполняет фоновый проход, поэтому фактический момент удаления может отставать от истечения `autoDeleteSeconds`. Правила фоновой очистки описаны в [`architecture.md`](architecture.md).
- Удаление слота не продлевает время жизни консюмера.

### Формат тела ошибки

- Ошибочный ответ содержит код состояния `4xx` или `5xx` и JSON-объект с текстовым описанием ошибки. Тело ошибки не является пустым.
- Гарантированной частью контракта является код состояния: логика теста должна опираться на него. Структура полей тела ошибки фиксируется в OpenAPI-спецификации по `/api-docs`; тест не должен зависеть от текста сообщения.
- Отсутствие сущности и недопустимый параметр различаются кодом состояния: отсутствие слота или проверки — `404`, недопустимое значение параметра — `400`, конфликт состояния при удалении слота во время ожидания — `409`.

### Ограничения сервиса

- **Одна реплика.** Состояние слотов, накопленных записей и ожиданий хранится только в памяти процесса. Горизонтальное масштабирование не поддерживается; при перезапуске все слоты и накопленные записи теряются, и слот нужно регистрировать заново.
- **Отсутствие аутентификации и авторизации.** Клиенты API не аутентифицируются, права доступа не проверяются, квоты и ограничение частоты запросов не применяются.
- **Отсутствие персистентности.** Реестры слотов, консюмеров и ожиданий не сохраняются на диск; история записей топика не хранится и не воспроизводится.
- **Целевая нагрузка 10–50 RPS.** Пропускная способность не оптимизируется под высокие нагрузки.
- **Мягкая гарантия доставки.** Запись попадает в слот только если консюмер уже читает соответствующий топик; записи, прошедшие до регистрации первого слота по топику, в слот не попадают.

### Особенности асинхронного ожидания

- Единственный метод с отложенным ответом — `POST /api/v1/slots/{id}/checks/{index}/wait`. Остальные методы завершаются до возврата ответа и не зависят от будущих событий.
- Поток обработки запроса не удерживается: ожидание регистрируется, управление возвращается в цикл обработки запросов, а ответ формируется по событию. Синхронных ожиданий и опроса счётчиков нет.
- Результаты ожидания различимы кодами: `200` — условие выполнено, `504` — истёк тайм-аут, `409` — слот удалён и наблюдение прекращено. Тест не должен трактовать `409` как тайм-аут.
- Тайм-аут не отменяет накопление: записи, пришедшие после `504`, остаются в слоте и доступны методам подсчёта и чтения.
- Ожидание по проверке не влияет на другие ожидания того же слота и на ожидания других слотов.
