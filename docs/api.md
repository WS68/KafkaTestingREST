## Общие сведения и правила контракта

### Базовый путь и формат обмена

- Базовый путь всех методов — `/api/v1`. Полные пути приведены в описании каждого метода.
- Обмен выполняется в формате JSON: запросы с телом передают `Content-Type: application/json`, ответы возвращаются с JSON-телом.
- Имена полей передаются в кодовом написании и регистрозависимы: `topic`, `headers`, `name`, `type`, `data`, `value`, `key`, `checks`, `values`, `jsonPath`, `autoDeleteSeconds`, `count`, `offset`, `ack`, `id`, `n`, `timeoutMs`. Переименование полей не допускается.
- Бинарные данные на границе JSON/HTTP представляются base64-строкой. В Kafka передаются исходные байты; base64 не является форматом хранения в топике.
- Идентификатор слота — строка. Индекс проверки — целое число, отсчёт начинается с нуля и соответствует позиции элемента в массиве `checks` запроса регистрации слота.
- Успешный ответ, не возвращающий данных, содержит тело `{}`. Ответ, возвращающий данные, содержит JSON-объект или массив объектов описанной структуры.
- Тело ответа определяется описанием конкретного метода. В частности, ответ ожидания с кодом `504` содержит `{}`, а не описание ошибки. Для остальных ошибочных ответов исходные требования не задают структуру тела; указания на JSON-объект с описанием ошибки ниже являются допущением до сверки с собственной OpenAPI-спецификацией и реализацией.

### Источники и статус уточнений

Исходный состав методов, полей и явно заданных кодов состояния перенесён из раздела API в [`../readme.md`](../readme.md). В репозитории нет исходного кода сервиса и собственной сохранённой спецификации OpenAPI; проверка работающего сервиса не выполнялась. Поэтому соответствие документа фактической реализации и собственной спецификации по `/api-docs` пока не подтверждено.

Файл [`../misc/openapi.yaml`](../misc/openapi.yaml) — внешняя спецификация Confluent Kafka REST v3, описывающая REST-прокси Kafka. Это не OpenAPI-спецификация этого сервиса: она не изменяется, слоты и значения по умолчанию этого сервиса в неё не добавляются, а её положения используются только как описание формата вызова внешнего REST-прокси. Требования к преобразованию типов, кодировке UTF-8, base64 и значениям по умолчанию, изложенные ниже, являются требованиями контракта этого сервиса.

Существующие уточнения, которые не определены явно в исходных требованиях, следует считать **допущениями**, а не проверенным поведением:

- обязательность полей, допустимые типы и ограничения, не заданные явно в исходном описании, включая необязательность заголовков и ключа, обязательность значения и непустой набор проверок;
- необязательность `ack` и его значение по умолчанию `1`, смещение (`offset`) по умолчанию `0`, применение `defaultWaitSeconds` при отсутствии `timeoutMs` с переводом секунд в миллисекунды;
- код `201` при регистрации слота, коды `400` и `503` при её отказе, дополнительные коды `400` и `404` для ожидания, подсчёта и чтения, а также структура тел ошибок;
- внешние особенности, уточнённые на основе [`architecture.md`](architecture.md), включая автоматическое удаление и независимость накопления от ожиданий;
- коды ответа и представление в ответе чтения записи с некорректным JSON или недекодируемыми как UTF-8 байтами заголовка: гарантировано только несовпадение соответствующих условий проверки, остальная политика исходными требованиями не определена.

Явно заданные исходными требованиями коды и тела ответов сохраняются без изменения. Допущения требуют сверки при появлении реализации и собственной OpenAPI-спецификации; этот документ не заменяет такую проверку.

### Общая структура описания методов

Каждый метод описан по единому шаблону: назначение, метод и путь, параметры пути, параметры запроса, тело запроса, тело ответа, коды состояния, особенности. Обозначения `{name}`, `{id}` и `{index}` заменяются значениями параметров пути; `0/1` означает выбор одного значения `ack`, а `NNNN`, `ms`, `N` и `M` — значения параметров запроса. Это условные обозначения, а не буквальные значения в запросе; в тела JSON-примеров они не входят.

### Сводная таблица методов

| Метод | Путь | Назначение | Успешный код |
| --- | --- | --- | --- |
| `POST` | `/api/v1/topics/{name}/records` | Публикация записи в топик через Kafka REST API | `201` или `202` |
| `POST` | `/api/v1/slots` | Регистрация слота с набором проверок | `201` |
| `POST` | `/api/v1/slots/{id}/checks/{index}/wait` | Асинхронное ожидание записей под проверкой | `200` |
| `GET` | `/api/v1/slots/{id}/checks/{index}/count` | Подсчёт записей, попавших под проверку | `200` |
| `GET` | `/api/v1/slots/{id}/checks/{index}` | Чтение записей, попавших под проверку | `200` |
| `DELETE` | `/api/v1/slots/{id}` | Удаление слота до истечения `autoDeleteSeconds` | `200` |

### Рекомендуемая последовательность вызова

1. Зарегистрировать слот с проверками методом `POST /api/v1/slots` и сохранить полученный `id`.
2. Инициировать тестируемую операцию, при необходимости опубликовав запись методом `POST /api/v1/topics/{name}/records`.
3. Дождаться нужного числа записей методом `POST /api/v1/slots/{id}/checks/{index}/wait` либо проверить их количество методом `GET /api/v1/slots/{id}/checks/{index}/count`.
4. Прочитать накопленные записи методом `GET /api/v1/slots/{id}/checks/{index}`.
5. Удалить слот методом `DELETE /api/v1/slots/{id}`, если он больше не нужен.

Порядок шагов 1 и 2 важен для теста: слот наблюдает только записи, полученные после его регистрации. Консюмер начинает чтение с конца разделов топика, поэтому записи, пришедшие до открытия слота или за время, пока консюмер был закрыт, в слот не попадают. Почему это так, описано в [`architecture.md`](architecture.md).

## Формат `RecordDto`

`RecordDto` — структура записи в теле запроса публикации. Запись, полученная из Kafka, возвращается методом чтения в отдельном JSON-ограниченном представлении. Причина различия: Kafka хранит только байты и не сохраняет типовую метку из HTTP-запроса, поэтому входная типизированная модель и представление полученной записи описываются раздельно.

Исходная типовая метка при чтении не восстанавливается, поэтому представление чтения не является копией исходного запроса. При этом корректно представленный объект чтения может быть опубликован снова по правилам модели публикации: отсутствие `type` у заголовков покрывается типом по умолчанию `STRING`, а `value` с типом `JSON` допустимо для публикации. Побайтовое сохранение исходного JSON при такой повторной публикации не гарантируется, поскольку значение сериализуется заново.

### Модель публикации

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `headers` | массив объектов | Нет | Набор заголовков записи; при отсутствии запись передаётся без заголовков |
| `headers[].name` | строка | Да, если элемент задан | Имя заголовка; остаётся обычной строкой и не типизируется |
| `headers[].type` | строка, закрытый перечень `STRING`, `BINARY`, `JSON` | Нет | Тип полезных данных заголовка; при отсутствии применяется `STRING` |
| `headers[].value` | строка или JSON-данные | Да, если элемент задан | Полезные данные заголовка: строка для `STRING` и `BINARY`, JSON-данные для `JSON` |
| `key` | объект | Нет | Ключ записи; при отсутствии запись передаётся без ключа |
| `key.type` | строка, закрытый перечень `STRING`, `BINARY`, `JSON` | Нет | Тип ключа; при отсутствии применяется `STRING` |
| `key.data` | строка или JSON-данные | Да, если `key` задан | Полезные данные ключа: строка для `STRING` и `BINARY`, JSON-данные для `JSON` |
| `value` | объект | Да | Значение записи |
| `value.type` | строка, закрытый перечень `STRING`, `BINARY`, `JSON` | Нет | Тип значения; при отсутствии применяется `JSON` |
| `value.data` | строка или JSON-данные | Да | Полезные данные значения: строка для `STRING` и `BINARY`, JSON-данные для `JSON` |

### Правила преобразования в байты

- В Kafka всегда передаются исходные байты. Base64 — только представление двоичных данных на границе JSON/HTTP и не является форматом хранения в Kafka.
- `STRING`: полезные данные — текст, который кодируется в UTF-8 без добавления JSON-кавычек.
- `JSON`: полезные данные — JSON-данные, которые сериализуются в JSON ровно один раз и кодируются в UTF-8. Объект остаётся объектом и не превращается в строку с экранированным JSON. Если `data` само является JSON-строкой, кавычки и экранирование — нормальная обязательная часть её однократной сериализации, а не признак двойной сериализации; автоматический разбор текста JSON внутри строк не выполняется. Сравнение: `STRING` с `data` `foo` даёт байты `foo`, а `JSON` с `data`, равным JSON-строке `foo`, — байты JSON-текста `"foo"`, где кавычки входят в данные.
- `BINARY`: полезные данные — base64-строка, которая декодируется в исходные байты перед публикацией. Публикуются именно исходные байты, а не UTF-8-байты текста base64. Двойное кодирование запрещено: `Zm9vYmFy` превращается в байты `66 6f 6f 62 61 72` (`foobar`), а не в байты строки `Zm9vYmFy`.
- При чтении выполняется обратное преобразование согласно разделу «Представление полученной записи»: ключ представляется base64-строкой исходных байтов, заголовки — строками UTF-8, значение — разобранным JSON.
- Тип по умолчанию применяется только при отсутствии `type`: `STRING` для `key` и значений заголовков, `JSON` для `value`. Если `type` задан неизвестным значением, не соответствует форме `data` или `data` для `BINARY` не является корректной base64-строкой, данные считаются недопустимыми и не публикуются; незаметное преобразование по умолчанию не выполняется. Конкретный код ответа для такого случая исходными требованиями не определён.
- JSON сериализуется заново, поэтому пробелы и порядок полей исходного JSON не гарантируются. Типы `STRING` и `JSON` различаются только способом получения байтов: строка `{"foo":"bar"}` с типом `STRING` даёт UTF-8-байты этого текста, а JSON-данные `{"foo":"bar"}` с типом `JSON` дают байты сериализованного JSON. Kafka не сохраняет метку типа, поэтому при чтении исходное различие не восстанавливается.

### Форма типизированного заголовка

Для заголовка используется минимальная обратно совместимая по форме запись `{name, type, value}`:

- `name` — обычная строка, имя заголовка не типизируется;
- `type` — необязательное поле закрытого перечня `STRING`, `BINARY`, `JSON`; при отсутствии применяется `STRING`;
- `value` — полезные данные: JSON-данные для `JSON`, строка для `STRING` и `BINARY`.

Такая форма сохраняет существующее поле `headers[].value` и не вводит неоднозначное вложение `value.value`. Одновременная поддержка двух форм заголовка не предусмотрена.

### Представление полученной записи

| Поле | Тип | Назначение |
| --- | --- | --- |
| `headers[].name` | строка | Имя заголовка |
| `headers[].value` | строка | Значение заголовка, полученное строгим декодированием его байтов как UTF-8; base64 не применяется |
| `key.type` | строка | Всегда `BINARY`: обозначение способа представления произвольных байтов в JSON, а не исходного типа публикации |
| `key.data` | строка | Base64 исходных байтов ключа |
| `value.type` | строка | Всегда `JSON` |
| `value.data` | JSON-данные | JSON-значение, полученное разбором UTF-8-байтов значения |

- Если запись не имеет ключа или заголовков, конкретная форма их отсутствия в ответе чтения — отсутствие поля или значение `null` — исходными требованиями не определена.
- Поддерживается только JSON UTF-8 для значения полученной записи; двоичное тело ответа чтения не является поддерживаемым вариантом.
- Если байты заголовка не декодируются как UTF-8, представление такого заголовка в ответе чтения исходными требованиями не определено.
- Если байты значения не являются корректным UTF-8 JSON, представление значения в ответе чтения исходными требованиями не определено.
- Исходный тип `STRING`, `BINARY` или `JSON`, указанный при публикации, в Kafka не сохраняется и при чтении не восстанавливается.

### Пример: публикация значения типа `JSON`

```json
{
  "headers": [
    {
      "name": "correlationId",
      "value": "corr-123"
    },
    {
      "name": "binaryTrace",
      "type": "BINARY",
      "value": "dHJhY2UtNDI="
    }
  ],
  "key": {
    "type": "STRING",
    "data": "order-42"
  },
  "value": {
    "type": "JSON",
    "data": {
      "orderId": "42",
      "status": "CREATED"
    }
  }
}
```

У заголовка `correlationId` тип не задан, поэтому применяется `STRING`. Заголовок `binaryTrace` декодируется из base64 в байты `trace-42`. Ключ передаётся как UTF-8-байты текста `order-42`, значение — как UTF-8-байты сериализованного JSON.

### Пример: публикация значения типа `BINARY`

```json
{
  "headers": [],
  "key": {
    "type": "STRING",
    "data": "order-42"
  },
  "value": {
    "type": "BINARY",
    "data": "Zm9vYmFy"
  }
}
```

Значение `Zm9vYmFy` декодируется в байты `66 6f 6f 62 61 72` (`foobar`), а не в байты текста `Zm9vYmFy`.

### Пример: представление полученной записи

```json
{
  "headers": [
    {
      "name": "correlationId",
      "value": "corr-123"
    }
  ],
  "key": {
    "type": "BINARY",
    "data": "b3JkZXItNDI="
  },
  "value": {
    "type": "JSON",
    "data": {
      "orderId": "42",
      "status": "COMPLETED"
    }
  }
}
```

Заголовок представлен UTF-8-строкой без base64 и без поля `type`; ключ — base64 исходных байтов; значение — разобранный JSON.

## Публикация записей в топики

### Назначение

Передача записи в топик Kafka через Kafka REST API. Метод позволяет тесту инициировать асинхронную операцию без собственного клиента Kafka. Результат публикации не зависит от того, открыт ли слот по этому топику: попадание записи в слот проверяется только методами ожидания, подсчёта и чтения.

### Метод и путь

`POST /api/v1/topics/{name}/records?ack=0/1`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `name` | строка | Да | Имя топика, в который публикуется запись |

### Параметры запроса

| Параметр | Тип | Обязательность | Допустимые значения | Назначение |
| --- | --- | --- | --- | --- |
| `ack` | целое | Нет — допущение | `0`, `1`; значение по умолчанию `1` — допущение | Режим подтверждения отправки |

Значения `ack`:

| Значение | Смысл | Код успешного ответа |
| --- | --- | --- |
| `1` | Сервис дожидается подтверждения брокера и сообщает, что отправка подтверждена | `201` |
| `0` | Сервис не дожидается подтверждения брокера и сообщает, что сообщение принято к отправке | `202` |

### Тело запроса

Тело — объект модели публикации, описанной в разделе «Формат `RecordDto`». Обязательным является поле `value`; поля `headers` и `key` необязательны. Пример с полностью опущенными `type` показывает применение значений по умолчанию:

```json
{
  "headers": [
    {
      "name": "correlationId",
      "value": "corr-123"
    }
  ],
  "key": {
    "data": "order-42"
  },
  "value": {
    "data": {
      "orderId": "42",
      "status": "CREATED"
    }
  }
}
```

Здесь заголовок и ключ интерпретируются как `STRING`, значение — как `JSON`.

### Передача в Kafka REST API

- Для `key` и `value` сервис передаёт внешнему Kafka REST API объект с явным полем `type` после применения значений по умолчанию: `STRING` для ключа и `JSON` для значения, если тип не задан.
- Заголовки внешнего Kafka REST API описываются парой `{name, value}`, где `value` — base64, и не имеют поля `type`. Поэтому типизированный заголовок сначала преобразуется в исходные байты по правилам выше, а затем кодируется в base64 для REST-прокси. REST-прокси восстанавливает исходные байты; повторное кодирование base64 не выполняется.
- При прямом клиенте Kafka в топик сразу передаются исходные байты без промежуточного base64.
- Внешняя спецификация Confluent Kafka REST v3 в [`../misc/openapi.yaml`](../misc/openapi.yaml) описывает REST-прокси, а не HTTP API этого сервиса. Она не изменяется, и слоты, значения по умолчанию и правила преобразования типов этого сервиса в неё не добавляются. Точные правила UTF-8, base64 и значений по умолчанию являются требованиями контракта этого сервиса, а не дословно установленными внешней спецификацией.

### Тело ответа

Тело успешного ответа (`201` или `202`) — пустой JSON-объект. Тело ответа при недопустимом топике исходными требованиями не определено.

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `201` | Отправка подтверждена брокером; возвращается при `ack=1` | `{}` |
| `202` | Сообщение принято к отправке без ожидания подтверждения брокера; возвращается при `ack=0` | `{}` |
| `400` | Список `publisherTopics` непуст и имя топика не соответствует ни одному его регулярному выражению | JSON-объект с описанием ошибки — допущение; исходные требования тело не определяют |

### Особенности

- Допустимость топика определяется параметром `publisherTopics`. Правила конфигурации см. в [`configuration.md`](configuration.md). Порядок проверки до обращения к Kafka описан в [`architecture.md`](architecture.md).
- Тип задаётся закрытым перечнем `STRING`, `BINARY`, `JSON`. Значения по умолчанию применяются только при отсутствии `type`: `STRING` для `key` и значений заголовков, `JSON` для `value`. При неизвестном или некорректном `type`, несоответствии формы `data` выбранному типу или некорректной base64-строке для `BINARY` данные не публикуются и не заменяются значением по умолчанию: ошибочные данные не должны незаметно преобразовываться.
- Режим `ack` влияет только на то, дожидается ли сервис подтверждения брокера; на состав слотов и накопление записей публикация не влияет.
- При недоступности Kafka REST API публикация считается неуспешной. Исходные требования не определяют конкретный код состояния и тело ответа для этого случая; их необходимо сверить с собственной спецификацией OpenAPI при появлении реализации. Обработка отказа описана в [`architecture.md`](architecture.md).
- Метод не возвращает идентификатор слота и не содержит признака попадания записи в слот.
- Задержка между успешным ответом публикации и появлением записи в слоте определяется Kafka и сервисом не гарантируется; поэтому ожидание реализовано асинхронным с тайм-аутом.

## Регистрация слота и проверок

### Назначение

Создание слота — точки наблюдения за топиком. С момента регистрации слота начинают заполняться результаты его проверок: каждая полученная из топика запись сопоставляется с проверками слота, и подходящие записи накапливаются. Слот привязывается к одному топику и неизменяемому набору проверок; обычно слот регистрируется по идентификатору корреляции.

### Метод и путь

`POST /api/v1/slots`

### Параметры пути

Метод не имеет параметров пути.

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `topic` | строка | Да | Имя наблюдаемого топика |
| `autoDeleteSeconds` | целое, больше нуля | Нет | Срок автоматического удаления слота в секундах, отсчитываемый от момента регистрации |
| `checks` | непустой массив объектов | Да | Набор проверок слота; позиция элемента задаёт `index` в путях остальных методов |
| `checks[].headers` | массив объектов | Нет | Ожидаемые заголовки записи; пустой набор не накладывает ограничения |
| `checks[].headers[].name` | строка | Да, если элемент задан | Имя ожидаемого заголовка |
| `checks[].headers[].value` | строка | Да, если элемент задан | Ожидаемое значение заголовка — обычная UTF-8-строка, а не base64 |
| `checks[].values` | массив объектов | Нет | Ожидаемые значения, извлекаемые из значения записи по `jsonPath`; пустой набор не накладывает ограничения |
| `checks[].values[].jsonPath` | строка | Да, если элемент задан | Путь к значению внутри значения записи |
| `checks[].values[].value` | строка | Да, если элемент задан | Ожидаемое значение, сравниваемое как строка |

Правила сопоставления:

- Байты заголовка полученной записи строго декодируются как UTF-8; полученная строка сравнивается с `checks[].headers[].value` как обычная строка. При ошибке декодирования сверка этого заголовка ложна; ошибочные байты не заменяются символом замены.
- Проверяется только тот заголовок, который указан в проверке. Наличие другого заголовка с недекодируемыми байтами не отвергает запись, если этот заголовок не участвует в проверке.
- `checks[].values` применимы только к значению записи, представленному как JSON UTF-8. Если значение не декодируется как UTF-8 или не является корректным JSON, условия `values` и `jsonPath` этой проверки гарантированно не совпадают. Отдельный код ответа и отбрасывание всей записи для такого случая исходными требованиями не определены.
- Условия одной проверки соединяются логическим И: запись удовлетворяет проверке только при совпадении всех указанных заголовков и всех указанных значений.
- Имя заголовка в проверке — обычная строка и не типизируется; `type` для ожидаемых заголовков не задаётся. Значение сравнивается как строка, а не как JSON-структура: структурное сравнение заголовков не применяется.

Пример запроса:

```json
{
  "topic": "orders.results",
  "autoDeleteSeconds": 300,
  "checks": [
    {
      "headers": [
        {
          "name": "correlationId",
          "value": "corr-123"
        }
      ],
      "values": [
        {
          "jsonPath": "$.status",
          "value": "COMPLETED"
        }
      ]
    },
    {
      "values": [
        {
          "jsonPath": "$.orderId",
          "value": "42"
        }
      ]
    }
  ]
}
```

В примере слот содержит две проверки: проверка с индексом `0` требует совпадения заголовка `correlationId` со строкой `corr-123` и значения `$.status`, проверка с индексом `1` — только значения `$.orderId`.

### Тело ответа

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | строка | Идентификатор созданного слота; используется во всех последующих методах работы со слотом |

```json
{
  "id": "3f6b1a2c-9d4e-4b7a-8c1a-2e5f7a9b0c3d"
}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `201` | Слот зарегистрирован; выбор кода является допущением, поскольку исходные требования задают только тело ответа | JSON-объект с полем `id`, как в примере выше |
| `400` | Тело запроса недопустимо: отсутствует `topic`, отсутствует или пуст `checks`, нарушена структура элемента проверки | JSON-объект с описанием ошибки |
| `503` | Не удалось создать консюмер топика: клиент Kafka не инициализирован или подписка не выполнена | JSON-объект с описанием ошибки |

### Особенности

- Если `autoDeleteSeconds` не задано, используется параметр `autoDeleteSlotsSeconds`, как установлено исходными требованиями. Правила конфигурации см. в [`configuration.md`](configuration.md).
- Запись удовлетворяет проверке только при совпадении **всех** её параметров: каждого ожидаемого заголовка и каждого значения, извлечённого по `jsonPath`. Несовпадение хотя бы одного параметра означает, что запись в эту проверку не попадает; частичного накопления не существует.
- Правила обработки пустых условий, ошибок вычисления `jsonPath` и совпадений с несколькими проверками описаны в разделе «Модель проверок и асинхронного ожидания» документа [`architecture.md`](architecture.md).
- Срок слота не продлевается ни поступлением записей, ни операциями чтения, ни регистрацией ожиданий.
- Если создание консюмера завершилось отказом, слот не регистрируется и частичного состояния не остаётся; порядок отката описан в [`architecture.md`](architecture.md).

## Асинхронное ожидание записей

### Назначение

Ожидание момента, когда под проверку попадёт заданное число записей. Метод избавляет тест от синхронного опроса счётчика: ответ откладывается до выполнения условия или до истечения тайм-аута, а поток обработки запроса не блокируется.

### Метод и путь

`POST /api/v1/slots/{id}/checks/{index}/wait?n=NNNN&timeoutMs=ms`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота, полученный при регистрации |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

| Параметр | Тип | Обязательность | Значение по умолчанию | Ограничения | Назначение |
| --- | --- | --- | --- | --- | --- |
| `n` | целое | Нет | `1` | Больше или равно `1` | Требуемое число записей, попавших под проверку |
| `timeoutMs` | целое | Нет | Значение `defaultWaitSeconds`, переведённое из секунд в миллисекунды; допущение | Больше нуля; значение задаётся в миллисекундах | Предельное время ожидания |

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

При выполнении условия (`200`) и при истечении тайм-аута (`504`) тело ответа — пустой JSON-объект. Метод не возвращает накопленные записи; для их получения используется метод чтения.

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Условие выполнено: под проверку попало не менее `n` записей | `{}` |
| `504` | Условие не выполнено за отведённое время, тайм-аут истёк | `{}` |
| `409` | Слот удалён — вручную или по истечении `autoDeleteSeconds` — до завершения ожидания | JSON-объект с описанием ошибки |
| `404` | Слот с указанным `id` отсутствует либо `index` выходит за границы набора проверок слота | JSON-объект с описанием ошибки |
| `400` | Значения `n` или `timeoutMs` недопустимы: не являются целыми числами, `n` меньше `1`, `timeoutMs` не больше нуля | JSON-объект с описанием ошибки |

### Особенности

- Ответ откладывается до выполнения условия или истечения тайм-аута; поток обработки запроса не удерживается, блокирующих пауз и опроса счётчика не выполняется. Механизм отложенного завершения описан в [`architecture.md`](architecture.md).
- Если требуемое число записей уже накоплено, ответ возвращается без ожидания новых записей.
- Тайм-аут завершает ожидание результатом «тайм-аут» и не влияет на накопление: записи, пришедшие позже, остаются в слоте и доступны методам подсчёта и чтения.
- При отсутствии `timeoutMs` принято использовать `defaultWaitSeconds` с переводом секунд в миллисекунды. Правила конфигурации см. в [`configuration.md`](configuration.md). Связь параметра запроса с параметром конфигурации является допущением, отмеченным выше.
- Удаление слота во время ожидания завершает ожидание отдельным результатом «слот удалён», который преобразуется в ошибку конфликта состояния `409`. Тест должен трактовать `409` как прекращение наблюдения, а не как истечение времени: коды `504` и `409` различимы и означают разные события.
- При одновременном выполнении условия и истечении тайм-аута возможен один из ответов: `200` или `504`; ответ формируется однократно, а запись остаётся в слоте. Правило разрешения этой ситуации описано в [`architecture.md`](architecture.md).
- Ожидание не изменяет накопление: записи продолжают собираться и после разрешения ожидания.
- Несколько ожиданий по одному слоту и одной проверке допустимы и завершаются независимо.

## Подсчёт записей проверки

### Назначение

Получение текущего числа записей, попавших под проверку. Метод не ждёт новых записей и возвращает снимок счётчика на момент обработки запроса.

### Метод и путь

`GET /api/v1/slots/{id}/checks/{index}/count`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

| Поле | Тип | Назначение |
| --- | --- | --- |
| `count` | целое | Число записей, попавших под проверку с момента регистрации слота |

```json
{
  "count": 2
}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот и проверка существуют | JSON-объект с целочисленным полем `count`, как в примере выше |
| `404` | Слот с указанным `id` отсутствует — удалён вручную или по сроку | JSON-объект с описанием ошибки |
| `404` | `index` выходит за границы набора проверок слота или не является целым числом | JSON-объект с описанием ошибки |

### Особенности

- Счётчик охватывает все подходящие записи; лимит выборки (`count`) применяется только при чтении записей.
- Счётчик не сбрасывается при завершении ожиданий и при операциях чтения.
- После удаления слота накопленные записи и счётчики освобождаются, поэтому метод возвращает `404`.
- Операция синхронная: она не ожидает новых записей и завершается до возврата ответа.

## Чтение записей проверки

### Назначение

Получение записей, попавших под проверку, с постраничной выборкой. Метод возвращает снимок накопителя и не ожидает новых записей.

### Метод и путь

`GET /api/v1/slots/{id}/checks/{index}?offset=N&count=M`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |
| `index` | целое, больше или равно нулю | Да | Индекс проверки внутри слота |

### Параметры запроса

| Параметр | Тип | Обязательность | Значение по умолчанию | Ограничения | Назначение |
| --- | --- | --- | --- | --- | --- |
| `offset` | целое | Нет — допущение | `0` — допущение | Больше или равно нулю | Смещение (`offset`) — число записей, пропускаемых от начала накопленного списка |
| `count` | целое | Нет | `20` | Больше нуля | Лимит выборки (`count`) — максимальное число возвращаемых записей |

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

Массив объектов в представлении полученной записи, описанном в разделе «Формат `RecordDto`». Тело ответа — JSON; двоичное тело чтения не является поддерживаемым вариантом. Пустой результат возвращается пустым массивом.

```json
[
  {
    "headers": [
      {
        "name": "correlationId",
        "value": "corr-123"
      }
    ],
    "key": {
      "type": "BINARY",
      "data": "b3JkZXItNDI="
    },
    "value": {
      "type": "JSON",
      "data": {
        "orderId": "42",
        "status": "COMPLETED"
      }
    }
  },
  {
    "headers": [
      {
        "name": "correlationId",
        "value": "corr-123"
      }
    ],
    "key": {
      "type": "BINARY",
      "data": "b3JkZXItNDM="
    },
    "value": {
      "type": "JSON",
      "data": {
        "orderId": "43",
        "status": "COMPLETED"
      }
    }
  }
]
```

Значение заголовка возвращается как UTF-8-строка без base64; ключ — base64 исходных байтов; значение — разобранный JSON.

Пустой результат:

```json
[]
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот и проверка существуют | Массив записей в представлении полученной записи |
| `404` | Слот с указанным `id` отсутствует — удалён вручную или по сроку | JSON-объект с описанием ошибки |
| `404` | `index` выходит за границы набора проверок слота или не является целым числом | JSON-объект с описанием ошибки |
| `400` | Значения `offset` или `count` недопустимы: не являются целыми числами, `offset` меньше нуля, `count` не больше нуля | JSON-объект с описанием ошибки |

### Особенности

- Порядок записей в ответе соответствует порядку их поступления из Kafka. При чтении из нескольких разделов топика абсолютный порядок не гарантируется, поскольку он определяется Kafka.
- Если `offset` превышает число накопленных записей, возвращается пустой массив.
- Если `offset + count` превышает число накопленных записей, возвращаются все оставшиеся записи без ошибки.
- Операция синхронная: она не ожидает новых записей и не изменяет накопитель. Для ожидания появления записей используется метод асинхронного ожидания.
- После удаления слота накопленные записи освобождаются, поэтому метод возвращает `404`.
- Значение записи представляется только как JSON UTF-8. Байты значения, не образующие корректный JSON, не могут быть представлены этим методом; политика их отображения исходными требованиями не определена. Байты заголовка, не декодируемые как UTF-8, также не имеют определённого представления.
- Исходный тип `STRING`, `BINARY` или `JSON`, заданный при публикации, в Kafka не сохраняется, поэтому по ответу чтения нельзя достоверно установить исходный тип. Пробелы и порядок полей JSON при сериализации также не гарантируются.

## Удаление слота

### Назначение

Досрочное удаление ненужного слота до истечения `autoDeleteSeconds`. Удаление освобождает накопленные записи и прерывает незавершённые ожидания этого слота.

### Метод и путь

`DELETE /api/v1/slots/{id}`

### Параметры пути

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | строка | Да | Идентификатор слота |

### Параметры запроса

Метод не имеет параметров запроса.

### Тело запроса

Метод не имеет тела запроса.

### Тело ответа

Тело успешного ответа — пустой JSON-объект.

```json
{}
```

### Коды состояния

| Код | Условие | Тело |
| --- | --- | --- |
| `200` | Слот существовал и удалён; накопленные записи освобождены, незавершённые ожидания прерваны | `{}` |
| `404` | Слот с указанным `id` отсутствует: удалён ранее вручную, удалён по истечении `autoDeleteSeconds` или никогда не существовал | JSON-объект с описанием ошибки |

### Особенности

- Все незавершённые запросы ожидания по этому слоту прерываются и завершаются с кодом `409`; тест получает признак прекращения наблюдения, а не истечения времени.
- Удаление идемпотентно по своему результату: повторный запрос по уже удалённому слоту не является ошибкой состояния реестра и возвращает `404` как признак отсутствия слота. Повторное удаление не изменяет состояние и безопасно для повторов.
- Записи, полученные консюмером после удаления, в слот не попадают. Методы подсчёта и чтения по удалённому слоту возвращают `404`.
- Слот остаётся доступным после истечения `autoDeleteSeconds` до фактического автоматического удаления; после него действуют те же ответы, что и после ручного удаления. Механизм очистки и влияние удаления на консюмер описаны в [`architecture.md`](architecture.md).

### Формат тела ошибки

- Ответ ожидания с кодом `504` содержит `{}` — это явно заданное исключение из предполагаемого формата тела ошибки.
- Для остальных ошибочных ответов исходные требования не определяют поля и обязательность тела. JSON-объект с описанием ошибки в таблицах выше — допущение, а не подтверждённая схема. Не следует придумывать имена полей или полагаться на текст сообщения; формат необходимо сверить с собственной спецификацией OpenAPI по `/api-docs` и реализацией.
- Код `409` при удалении слота во время ожидания и код `404` в ответе метода удаления заданы исходными требованиями. Различение отсутствия слота или проверки (`404`) и недопустимого значения параметра (`400`) для ожидания, подсчёта и чтения является уточнением, требующим проверки; предполагаемая обработка каждого случая приведена в таблице соответствующего метода.
- Для публикации с неизвестным или некорректным `type`, а также с `data` для `BINARY`, не являющимися корректной base64-строкой, код ответа исходными требованиями не определён; гарантировано лишь, что такие данные не публикуются и не подменяются значением типа по умолчанию.

### Ограничения сервиса

Архитектурные ограничения первой версии и их обоснование приведены в [`architecture.md`](architecture.md). Для клиента API существенны следующие последствия:

- После перезапуска требуется заново зарегистрировать слот; прежние идентификаторы и накопленные результаты не восстанавливаются.
- Слот следует регистрировать до инициирования тестируемой операции: уже прошедшие записи не воспроизводятся.
- Работа с несколькими репликами не предусмотрена; целевая нагрузка — 10–50 запросов в секунду.
- В принятой архитектуре аутентификация и авторизация не предусмотрены, квоты и ограничение частоты запросов не применяются.

### Особенности асинхронного ожидания

- Единственный метод с отложенным ответом — `POST /api/v1/slots/{id}/checks/{index}/wait`. Остальные методы завершаются до возврата ответа и не зависят от будущих событий.
- Механизм неблокирующего ожидания описан в [`architecture.md`](architecture.md); внешний контракт метода приведён в разделе «Асинхронное ожидание записей» выше.
- Результаты ожидания различимы кодами: `200` — условие выполнено, `504` — истёк тайм-аут, `409` — слот удалён и наблюдение прекращено. Тест не должен трактовать `409` как тайм-аут.
- Тайм-аут не отменяет накопление: записи, пришедшие после `504`, остаются в слоте и доступны методам подсчёта и чтения.
- Ожидание по проверке не влияет на другие ожидания того же слота и на ожидания других слотов.
