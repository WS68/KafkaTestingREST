# Правила работы с репозиторием

## Назначение и область действия

- Используй этот документ как обязательный набор правил для AI-агентов и контрибьюторов, работающих с кодом и документацией репозитория.
- Распространяй правила на корневые документы, пользовательский уровень в каталоге [`docs/`](docs/), инженерный уровень в каталоге `docs/specs/` (создаётся в рамках согласованного плана, задачи 3–5), каталог [`plans/`](plans/) и связанные с ними изменения в исходном коде, API и конфигурации.
- Считай каталог [`misc/`](misc/) каталогом справочных материалов. Используй его содержимое только при явном указании в задаче; не применяй материалы из [`misc/`](misc/) как источник требований или правил по умолчанию.
- Считай требования этого документа базовыми при создании, изменении, переносе и удалении материалов.
- При конфликте между этим документом и фактической реализацией сначала зафиксируй расхождение, затем согласуй документацию с актуальным поведением системы и обнови связанные материалы.

## Язык документации

- Пиши проектную документацию на русском техническом языке.
- Используй единую терминологию из глоссария ниже; не заменяй термины синонимами и не переводи их произвольно.
- Не смешивай русский текст с английскими терминами, если для термина существует устоявшийся русский аналог.
- Используй английские термины только для имён собственных, названий полей API, классов, заголовков HTTP и параметров конфигурации.
- При первом упоминании английского термина поясняй его назначение по-русски. Названия полей, классов, заголовков и параметров конфигурации оставляй без перевода в кодовом написании.
- Устраняй опечатки и грамматические ошибки в изменяемом фрагменте; не добавляй новые ошибки и не оставляй опечатки в новых правках.
- Распространяй требования русского технического языка, глоссарий и единое написание имён полей DTO и параметров конфигурации на пользовательские документы `docs/` и инженерные документы `docs/specs/`.
- Сохраняй одинаковое написание терминов, имён полей и путей во всех документах.

### Глоссарий терминов

В документации используй приведённые ниже русские термины. Английское соответствие указывай только при первом упоминании термина в документе или в скобках для однозначности.

| Термин в документации | Английское соответствие | Как употреблять |
| --- | --- | --- |
| слот | slot | Русское написание. Английское `slot` допустимо только в путях API и именах параметров конфигурации, например `autoDeleteSlotsSeconds`. |
| проверка | check | Русское написание. Английское `check` допустимо только в путях API и в имени поля `checks`. |
| консюмер | consumer | Русское написание «консюмер» во всём тексте; английское `consumer` остаётся только в именах параметров конфигурации (`consumerIdleSeconds`, `consumerGroupPrefix`). |
| публикация | publishing, publish | Русское написание для процесса отправки сообщений в Kafka. Английское `Publishing` допустимо только как заголовок исходного раздела требований. |
| ожидание | wait | Русское написание для асинхронного ожидания записей. Английское `wait` остаётся только в путях API. |
| топик | topic | Русское написание. Английское `topic` остаётся только в пути API и в имени поля `topic`. |
| запись | record | Русское написание для сообщения, полученного из Kafka. Английское `record` остаётся только в путях API и в имени класса `RecordDto`. |
| смещение | offset | Русское написание «смещение»; при первом упоминании указывай `offset`. Английское `offset` остаётся в именах параметров запроса. |
| лимит выборки | count | Русское написание «лимит выборки»; при первом упоминании указывай `count`. Английское `count` остаётся в именах параметров запроса и в поле ответа. |
| ключ | key | Русское написание. Английское `key` остаётся только в имени поля DTO. |
| значение | value | Русское написание. Английское `value` остаётся только в имени поля DTO. |
| заголовок | header | Русское написание. Английское `headers` остаётся только в имени поля DTO. |

Без перевода в кодовом написании оставляй имена полей DTO и параметров конфигурации: `topic`, `headers`, `key`, `value`, `checks`, `values`, `jsonPath`, `autoDeleteSeconds`, `cluster`, `publisherTopics`, `autoDeleteSlotsSeconds`, `consumerIdleSeconds`, `consumerGroupPrefix`, `defaultWaitSeconds`, `offset`, `count`, `ack`. Написание этих имён должно совпадать во всех документах и с реализацией.

## Расположение материалов

- Оставляй в корне репозитория только [`readme.md`](readme.md), [`AGENTS.md`](AGENTS.md), [`LICENSE`](LICENSE) и файлы сборки или обязательные файлы конфигурации инструментария.
- Размещай всю проектную документацию в каталоге [`docs/`](docs/). Пользовательский уровень состоит ровно из трёх документов: [`docs/api.md`](docs/api.md) описывает внешний контракт HTTP API, [`docs/architecture.md`](docs/architecture.md) — назначение сервиса, основные возможности и наблюдаемые пользователем ограничения, [`docs/configuration.md`](docs/configuration.md) — пользовательские параметры и практически значимые ограничения.
- Размещай инженерные спецификации только в каталоге `docs/specs/`. Инженерный уровень состоит ровно из трёх документов, которые создаются в рамках согласованного плана, задач 3–5: `docs/specs/api.md` описывает технические детали HTTP-реализации и подготовки DTO, `docs/specs/architecture.md` — внутреннюю архитектуру и инженерные решения, `docs/specs/configuration.md` — внутренний разбор, проверку и вычисления конфигурации.
- Фиксированный набор документации включает ровно эти три файла в `docs/` и ровно эти три файла в `docs/specs/`; новые документы в `docs/` или `docs/specs/` вне набора не создавай без отдельного обоснования и изменения настоящих правил.
- Источники правды распределяются следующим образом: внешний HTTP-контракт, публичные DTO, коды состояния и пользовательские примеры — только [`docs/api.md`](docs/api.md); внутренние алгоритмы, компоненты, состояния, инварианты, конкурентность, тестовая архитектура и архитектурные решения — только `docs/specs/architecture.md` (создаётся задачей 4); пользовательские параметры, переменные окружения, defaults, диапазоны и практически значимые ограничения — только [`docs/configuration.md`](docs/configuration.md); внутренний разбор, проверка, вычисление сроков, таймеры и формирование групп — только `docs/specs/configuration.md` (создаётся задачей 5); технические детали HTTP-реализации и подготовки DTO — только `docs/specs/api.md` (создаётся задачей 3), если тема не относится к общей архитектуре.
- Не дублируй содержание между уровнями. В спецификациях не повторяй таблицы DTO, обязательность полей, enum, коды ответов, defaults и пользовательские JSON-примеры; в пользовательских документах не описывай внутренние алгоритмы, компоненты, состояния и переходы, инварианты, конкурентность и блокировки, таймеры и завершение ресурсов, тестовую архитектуру, архитектурные решения, выбор Kafka-клиента и границу нативного транспорта. Для каждой темы назначай единственный источник правды, а в остальных местах используй краткую ссылку на него.
- В [`readme.md`](readme.md) оставляй назначение проекта, основные требования, инструкции по запуску или сборке и навигационные ссылки; подробные пользовательские сведения храни в соответствующих документах из [`docs/`](docs/), а инженерные сведения — в соответствующих спецификациях `docs/specs/`.
- Размещай планы работ только в каталоге [`plans/`](plans/), включая [`task_plan.md`](plans/task_plan.md).
- Рассматривай каталог [`misc/`](misc/) как справочные материалы, используемые только при явном указании в задаче. Не изменяй файлы в [`misc/`](misc/) и не переноси их содержание в проектную документацию без отдельного указания.

## Актуализация ссылок

- Используй относительные Markdown-ссылки для ссылок на файлы и каталоги внутри репозитория; это правило распространяется на `docs/` и `docs/specs/`.
- Направление ссылок между уровнями должно соответствовать границе содержания: пользовательский документ ссылается на инженерную спецификацию за техническими подробностями, а спецификация ссылается на пользовательский документ за публичным форматом и наблюдаемым поведением.
- Из `docs/*.md` в соответствующую спецификацию используй шаблон `specs/<имя>.md`; из `docs/specs/*.md` в соответствующий пользовательский документ используй шаблон `../<имя>.md`. Спецификации `docs/specs/api.md`, `docs/specs/architecture.md` и `docs/specs/configuration.md` создаются в рамках согласованного плана, задач 3–5, поэтому до их создания такие ссылки допустимы только с явным указанием этого статуса.
- Ссылка должна вести на конкретный раздел или подраздел, если она заменяет удалённое содержание; ссылка на весь документ допустима для навигации. При каждой ссылке с якорем проверяй существование целевого файла и корректность якоря.
- Проверяй работоспособность каждой изменённой и затронутой ссылки, существование её цели и корректность якоря при каждом изменении документации. Не оставляй «висячие» ссылки: ссылка должна вести на существующий файл или каталог либо явно указывать на материал, который создаётся в рамках текущего согласованного плана.
- При переименовании или переносе документа одновременно обновляй все перекрёстные ссылки на него в [`readme.md`](readme.md), [`AGENTS.md`](AGENTS.md), [`docs/`](docs/), `docs/specs/` и [`plans/`](plans/).
- Для ссылок из корневых файлов указывай путь относительно корня репозитория; для ссылок из вложенных документов учитывай каталог самого документа.
- Не используй абсолютные пути локальной файловой системы и ссылки, зависящие от рабочего окружения разработчика.

## Безопасность зависимостей

- Перед добавлением в проект нового пакета (зависимости) проверяй его на известные уязвимости.
- Если у выбранного пакета или его версии обнаружены уязвимости, обнови пакет до версии без уязвимостей либо замени компоненту на безопасную альтернативу.
- Не добавляй в проект пакет с известными уязвимостями, если доступны обновлённая версия или безопасная замена.
- Фиксируй в описании изменения результат проверки на уязвимости и принятое решение: обновление версии или замена компоненты.

## Согласованность API с OpenAPI

- Считай [`docs/api.md`](docs/api.md) описанием внешнего поведения HTTP API: методов, путей, параметров, тел, публичных DTO, кодов состояния, публичных ограничений и пользовательских примеров. Технические детали реализации, подготовки DTO, преобразования результатов и связи маршрутов со слоями храни в `docs/specs/api.md`, который создаётся в рамках согласованного плана, задачи 3.
- Поддерживай оба уровня документации в соответствии с фактической OpenAPI-спецификацией, доступной по `/api-docs`; интерфейс документации доступен по `/api-docs/swagger-ui`. `docs/api.md` описывает внешнее поведение, а `docs/specs/api.md` — инженерные детали; оба документа сверяй с OpenAPI, DTO, JSON Schema и фактической реализацией, не допуская расхождения публичного контракта.
- Перед изменением описания API сверяй метод, путь, параметры, DTO, обязательность полей, коды ответа и фактическое поведение реализации с OpenAPI. Изменение инженерной детали дополнительно сверяй с местом формирования маршрута, DTO или схемы в исходном коде.
- При любом изменении эндпоинта, DTO, JSON Schema, кода ответа или параметра одновременно обновляй [`docs/api.md`](docs/api.md), затронутые инженерные сведения в `docs/specs/api.md` и OpenAPI-описание в том месте, где оно формируется или хранится в исходном коде.
- Не считай изменение завершённым, пока пользовательская документация, инженерная спецификация, OpenAPI, DTO, JSON Schema и реализация не описывают один и тот же публичный контракт и согласованные инженерные детали.
- Проверяй, что каждый пример запроса и ответа в [`docs/api.md`](docs/api.md) и каждый JSON-пример, если он присутствует в спецификации, является валидным JSON: используй двойные кавычки для строк и имён свойств, не оставляй комментарии, лишние запятые или псевдотипы вроде `string` и `int` внутри JSON-примеров. Пользовательские JSON-примеры оставляй прежде всего в [`docs/api.md`](docs/api.md).
- Явно описывай в пользовательской документации назначение параметров запроса, структуру тела, коды успешных и ошибочных ответов, ограничения и особенности асинхронного ожидания; внутренние причины и алгоритмы описывай только в инженерной спецификации.

## Порядок внесения изменений в документацию

Перед фиксацией изменений последовательно проверь:

1. Использованы русские термины и устранены опечатки во всех изменённых пользовательских и инженерных документах; английские обозначения оставлены только в разрешённых именах и пояснены при первом упоминании.
2. Все новые и изменённые ссылки являются относительными, их цели и якоря существуют либо ссылка явно указывает на документ текущего согласованного плана, который ещё создаётся.
3. Все JSON-примеры, присутствующие в `docs/` или `docs/specs/`, синтаксически валидны и соответствуют описанным DTO.
4. Новое содержание не дублирует другой документ, размещено у единственного источника правды и соответствует границе пользовательского или инженерного уровня.
5. Внешнее поведение в [`docs/api.md`](docs/api.md) и инженерные детали в `docs/specs/api.md` согласованы с OpenAPI, DTO, JSON Schema и реализацией; публичный контракт не расходится.
6. Перекрёстные ссылки и навигация в [`readme.md`](readme.md), [`AGENTS.md`](AGENTS.md), `docs/`, `docs/specs/` и [`plans/`](plans/) обновлены после каждого переименования или переноса.
7. Изменения ограничены назначением соответствующего документа; исправления в исходных требованиях сопровождаются проверкой зависимых материалов.
