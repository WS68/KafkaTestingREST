# План реализации изменений документации и условий проверок

## Исходные решения и границы

- Документы `docs/api.md`, `docs/architecture.md` и `docs/configuration.md` сохраняются с прежними именами и предназначаются для пользователей сервиса: в них остаются назначение, внешнее поведение, способы вызова и пользовательские ограничения без внутренних алгоритмов и устройства компонентов.
- Подробности контракта, реализации и архитектурных решений переносятся в `docs/specs/api.md`, `docs/specs/architecture.md` и `docs/specs/configuration.md` соответственно. Спецификации являются инженерными документами и не дублируют пользовательское объяснение.
- Новые параметры применяются к каждому элементу внутри `checks[].values[]` и `checks[].headers[]`: `operation` принимает `EQUALS` или `CONTAINS`, отсутствие означает `EQUALS`; `ignoreCase` — логическое значение, отсутствие означает `false`.
- `CONTAINS` означает, что ожидаемая строка является подстрокой фактической. При `ignoreCase: true` обе строки сравниваются с использованием Unicode case folding, без Unicode-нормализации. Имена заголовков и `jsonPath` не меняют семантику сравнения.
- Публичный HTTP/OpenAPI-контракт должен совпадать с DTO, JSON Schema и фактическим поведением. Существующие запросы без новых полей сохраняют прежнее поведение.
- Плановые ориентиры для каждой отдельной задачи с кодированием: не более 100 строк производственного кода и 200 строк тестового кода. Если изменение больше, оно разбивается на дополнительные задачи; эти ориентиры не становятся ограничениями реализации.
